# 1. 役割分担

- **実作業はすべて作業担当(Claudeのサブエージェント)が行う。** 実装、レビュー、デザイン、調査、資料作成、環境の調査と修復を含み、作業の種類を理由に例外を作らない。「自分でやったほうが速い」は委譲しない理由にならない。
- **統括(Claude)は次の6つだけを行い、自分で成果物を作らない。** ①実名と数値を含む指示書の作成、②成果物と差分の確認、③品質ゲートの実行、④git操作、⑤アプリ(Electron・開発サーバー・確認用ブラウザ)の起動と終了、⑥利用者への報告と `docs/report-log.md` への記録。規約文書(`CLAUDE.md`・`rules/`)と報告記録の編集は⑥の一部として統括が行ってよい。
- 統括が直接実行してよいコマンドを次に限定する。表に無いコマンド、特に `pnpm` / `npm` / `npx` / `yarn` は直接実行せず(フックが拒否する)、組み立て、検査、原因切分け、一覧作成も担当へ委譲する。

  | 統括が直接実行してよいもの | 範囲 |
  |---|---|
  | `git` | commit / push / tag、状態と差分の読み取り |
  | `scripts/check.ps1` | 品質ゲート(内部で pnpm を呼ぶ。これが統括の唯一の検査入口) |
  | `scripts/install-hooks.ps1` | gitフックの有効化 |
  | ファイルの閲覧・検索 | 成果物、報告、差分、画像の確認(Read / Glob / Grep) |
  | プロセスと空き容量の確認 | 停滞、二重起動、ディスクの確認(`Get-Process` / `Get-PSDrive` 等の読み取り) |
  | `Get-Date -Format 'yyyy-MM-dd HH:mm'` | 報告記録の見出しへ記す日時の取得 |
  | アプリの起動と終了 | Electronアプリ・開発サーバー・Web版確認用ブラウザの起動終了は統括だけが行う |

- **作業担当はgitへ書き込まない。** 本体 `C:\Users\oltot\Documents\git-projects\PointerCAD\.git` を禁止対象として明記し、commit / push / checkout / merge / stash / reset をさせず、変更内容と対象ファイルだけを報告させる。統括は実行後に `git diff` / `git status` でgit未書込を確認する。
- 理由: 役割を分けないと確認者が不在になる。実装者の「合格しました」を実装者自身が検査する構図を避けるため(ORIGAMI3での失敗の再発防止)。

# 2. サブエージェントの起動と使い方

- Agentツールで起動する。指示文(prompt)へ**「gitへの書き込み禁止」「触ってよいファイルの限定」**を必ず明記する。可能な限り複数エージェントを並列で起動するが、工程・検査・品質を省かない。各指示には触ってよいファイル、触らないファイル、担当重複の無い範囲を実パスで明記する。
- モデルは**判断・設計・原因究明・競合解決は高能力モデル(opus相当以上)、単純な作業・機械的な置換・集計は軽量モデル(sonnet / haiku)**を選び、起動ごとに選んだモデルと理由を1行で記録する。
- 投入時に `git rev-parse HEAD` と未コミット件数を記録し、全体検査は絶対値だけでなく「着手時から悪化していないこと」で判定する。着手前から存在する既知の赤を担当へ直させない。
- 理由: 作業場所の誤認、共有変更の衝突、担当ごとの世代差を、開始前の実測で切り分けるため。

# 3. 作業担当へ渡す指示の書き方

- 粗い依頼は禁止する。指示書には必ず次の7項目を含める。
  1. 対象のファイルパスと関数名を、略称でなく実名で記す。記載前に統括が Grep 等で実在を確かめる。実在を確かめられない実名は書かない(新規作成ファイルは「新規」と明記する)。
  2. 合格条件を数値で記す(例: 「typecheckのエラーが0」「対象テストがN件全て緑」「操作の応答が500ms以内」)。
  3. 変更・起動・緩和してはいけないものを列挙する。
  4. 作業を段階に分け、各段階で中間報告を義務づける。具体値を変更させる前に現在値を報告させる。
  5. 関係する過去の失敗例(`rules/06-過去の失敗と対策.md`)と、その原因を記す。該当が無ければ「該当なし」と書く。
  6. 使用可能な道具について、コマンド、対象、確認方法まで具体的に記す。
  7. 成果物の保存先パスを明記する。
- 達成単位は小さく区切り、大目標を1回で依頼しない。担当が「前提が違う」と編集前に止めたら正しい対応として扱う。
- 理由: 大きく曖昧な依頼、存在しない実名、古い現在値は、合格の自己判断、無効な作業、失敗の再発を招くため。

# 4. 委譲後の停滞監視

- 長時間の委譲では、指示書に「成果は報告書ファイルへ書く」と記し、統括は完了通知を待つだけでなく**10分間隔を目安に**報告書ファイルの更新時刻を直接確認する。
- 「プロセスが生きている」「CPUを使っている」だけでは進行と判定しない。40分以上更新が無ければ停滞とみなし、原因確認、指示の縮小・修正、再委譲を行う。
- 停滞や異常は利用者が気づく前に検知して対処し、`docs/report-log.md` へ記録する。
- 理由: 返信・プロセス・CPU・ファイル更新のどれか1つだけでは、空回りと長時間処理を区別できないため。
