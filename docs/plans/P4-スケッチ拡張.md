# P4「スケッチ拡張」実装計画書

> **作業担当(サブエージェント)向け:** 本計画は `superpowers:subagent-driven-development`(推奨)または `superpowers:executing-plans` でタスク単位に実行する。各手順は `- [ ]` のチェックボックスで進捗を追う。
> **gitへの書き込みは統括だけが行う。** 作業担当は commit / push / checkout / merge / stash / reset を一切行わない(`rules/01-役割と委譲.md` §1)。

**目的:** 要件 `docs/requirements.md`(v1.3)§9 の P4 完了条件「板物・ブラケット程度の輪郭を線 1 本ずつ引かずに描いて整形でき、既存の立体の面・辺を投影して次の加工の下描きにできる。作業平面に依らない 3D スケッチで球面上の点や立体の頂点から線・面を作れ、表示テーマと拡大率を切り替えられる」を満たす。範囲は Must が矩形・正多角形・長穴・スプライン・楕円・構築線・オフセット・トリム/延長・スケッチのフィレット/面取り・ミラー/複写/配列複写・投影/交差・円と2点+半径の円弧・点列の拡張・任意の作業平面・基準軸/点/座標系(FR-314〜329)と 3D スケッチ(FR-330)、**最初の組として実装する**表示テーマの切替(FR-908)と表示の拡大率(FR-909)。Should が文字の輪郭化(FR-319)と寸法拘束・幾何拘束(FR-313)。

**構成方針:** P1〜P3 で確立した骨(`SketchDocument` に不変のフィーチャー履歴、`resolveSketch` が座標へ解決、`recomputeSketch` がカーネルで面を作る。`PartDocument` の `sketches` / `solids`、`resolvePart` が段へ畳む)を**そのまま使う**。P4 が足すのは次の 6 つに整理できる。

1. **表示テーマ(FR-908)と表示の拡大率(FR-909)。** 利用者の決定により**最初の組**として実装する。画面の見た目に関わるので、以後のタスクの目視確認の土台にもなる。
2. **新しい平面図形(矩形・正多角形・長穴・楕円・スプライン)。** いずれもスケッチの新しい種類で、矩形・正多角形・長穴は「1 フィーチャーが複数の線・円弧を生む」という P1〜P3 に無かった形を要る(§2.3)。
3. **既存要素を参照して整形する道具(構築線・オフセット・トリム/延長・スケッチのフィレット/面取り・ミラー/複写/配列複写)。** 「履歴として持つか、要素を書き換えるか」を道具ごとに決める(§2.5)。
4. **立体を参照するスケッチ(投影/交差・3D スケッチの立体頂点参照)。** スケッチが立体を参照するのは初めてで、`PartDocument` の `sketches` / `solids` が独立配列であるという P1〜P3 の前提と正面から衝突する(§2.7、**本計画で最もリスクが高い設計判断**)。
5. **任意の作業平面と基準ジオメトリ(基準軸・基準点・基準座標系)。** `WorkPlaneId` を固定 3 枚から文書内の任意平面フィーチャーへ広げる(§2.8)。
6. **3D スケッチ(FR-330)。** 新しい文書種は作らず、既存の `CoordinateInput` と `WorkPlaneId` の拡張の組み合わせで実現する(§2.4)。

**技術構成:** TypeScript(strict) / opencascade.js 2.0.0-beta.b5ff984(OCCT WASM、Worker + Comlink)/ fflate(ZIP)/ decimal.js(式)/ Three.js / React + Zustand / IndexedDB(自動保存)/ `localStorage`(表示設定)/ Vitest / Playwright。**P4 で追加する外部依存は原則 0 件**(§1。文字の輪郭化(Should)だけは opencascade.js 内の API を使うため依存追加は不要だが、実行時の挙動が未確認)。

**前提:** P3 のタスク 30(E2E の通しと全体検査)まで完了し、コミット済みであること。

## 2. 技術方式

### 2.1 P1〜P3 から引き継ぐもの / P4 が足すもの

**引き継ぐもの:** `SketchDocument` は不変のフィーチャー履歴のまま(`appendFeature` / `replaceFeature` / `removeFeature`)。`resolveSketch` が履歴を先頭から解決し、途中の失敗は `SketchError` として持ち回って止めない(FR-504)。`recomputeSketch` は面があるときだけカーネルを呼ぶ。座標は `CoordinateInput`(absolute / relative / polar)+ `PointReference` で持ち、複製しない。その場数値入力(`numericInput.ts` の状態機械)・道具の選択(`sketchCommands.ts` / `machiningCommands.ts` と同じ「純関数 + ストアが薄く包む」構成)・当たり判定と吸着(`pickMath.ts` / `snapMath.ts`)は同じ設計をそのまま延長する。

**P4 が足すもの:** ①表示テーマと拡大率(§2.2)。②複数曲線を生む図形(§2.3)。③3D スケッチ(§2.4)。④既存要素を参照する整形系道具(§2.5)。⑤立体を参照するスケッチ、`SubShapeRef` の移設を含む(§2.6・2.7)。⑥任意平面と基準ジオメトリ(§2.8)。

### 2.2 表示テーマ(FR-908)と表示の拡大率(FR-909、最初の組)

利用者の決定により、P4 の最初の組として実装する。

**テーマの切替:** `useAppStore` に `theme: 'dark' | 'light' | 'darkModern' | 'lightModern' | 'modern'`(既定 `'dark'`)を追加し、変更のたびにルート要素(`document.documentElement`)へ `data-theme` 属性を設定する。`appShell.css` の `:root` にある全 `--pcad-*` トークンを、5 テーマぶん `[data-theme="..."]` セレクタで定義する(`dark` は現行の `:root` の値をそのまま複製、`light` は明るい配色、`darkModern` / `lightModern` / `modern` は要件どおり「大きめの角丸と淡い影・広い余白・多めのアクセント色」を追加のトークン(`--pcad-radius-large` 等)で表現する)。three.js は CSS 変数を直接読めないため、`createViewportScene.ts` の背景色・グリッド色、`createSketchLayer.ts` の点・線・面の既定色を、起動時と `theme` 変更時に `getComputedStyle(document.documentElement).getPropertyValue('--pcad-...')` で読み直し、16 進数へ変換してマテリアルへ反映する関数(`readThemeColors()`)を新設する。

**拡大率:** `useAppStore` に `uiScale: number`(90〜150、既定 100)を追加し、`--pcad-scale`(0.9〜1.5)を `:root` へ設定する。`appShell.css` の数値系トークン(`--pcad-font-size`・`--pcad-font-size-heading`・`--pcad-font-size-small`・`--pcad-space-1〜4`・`--pcad-radius`・`--pcad-radius-small`)を `calc(既定px値 * var(--pcad-scale))` へ書き換える。

**設定の永続化と画面:** `packages/ui/src/settings/settings.ts`(新規)に `loadSettings()` / `saveSettings(settings)`(`localStorage` の 1 キー `pointercad.settings` に JSON で保存、壊れていれば既定値)を純関数として持つ。`SettingsPanel.tsx`(新規)はテーマ 5 種のプレビュー付きボタンと、拡大率のスライダー(90〜150、10%刻み)を持つ非モーダルの畳み一覧(`SnapKindsMenu` と同じ実装パターン)。`Toolbar.tsx` に歯車アイコンのボタンを 1 つ足し、`pcad-toolbar__actions`(製品名の隣、ファイル・履歴と同じグループ)へ置く(区画を増やさない)。

### 2.3 複数曲線を生む図形(矩形・正多角形・長穴)と単一曲線の図形(楕円・スプライン)

**矩形・正多角形・長穴の型:** いずれも「1 フィーチャーが複数の線・円弧の閉ループ(または開いた列)を生む」という共通の形を持つ。`SketchFeatureKind` に `'rectangle' | 'polygon' | 'slot'` を足し、それぞれの入力(矩形は対角 2 点または中心+幅+高さ、正多角形は中心+辺数+外接/内接半径、長穴は 2 中心点+幅または中心点+長さ+角度+幅)を保存する。

`resolveSketch.ts` に `curvesByFeature: Map<string, readonly ResolvedCurve[]>` を新設し(既存の `pointsByFeature: Map<string, readonly ResolvedPoint[]>` と対になる形)、矩形・正多角形・長穴の解決はここへ複数の `ResolvedSegment` / `ResolvedArc` を積む。`ResolvedSegment` / `ResolvedArc` の `featureId` は「そのフィーチャーの id」のままにし、`elementId`(点列と同じ `featureId#n` 形式)を picking・snap・面境界の各層へ通す。**この変更は `pickMath.ts` の `sketch.segments` / `sketch.arcs` の走査、`snapMath.ts` の候補収集、`buildSketchGeometry.ts` の描画に影響するため、いずれも `elementId` ベースで動くよう見直す**(現状は `featureId` = `elementId` の前提が線分・円弧の実装に埋め込まれている箇所があるため、Grep で洗い出す)。

`resolveFace` の境界解決(`SketchFaceFeature.boundary`)は `SketchElementRef.index` が未指定なら「そのフィーチャーの全曲線を順に展開」、指定されていれば「n 番目の曲線だけ」を採用するよう拡張する。

**楕円・楕円弧(FR-318):** 新しい `SketchFeatureKind` `'ellipse'`(中心・長軸半径・短軸半径・傾き・開始角度・終了角度)。1 フィーチャー = 1 `ResolvedCurve`(新設する `ResolvedEllipse` 種、または既存の `ResolvedArc` を長軸/短軸の 2 半径を持てるよう拡張するかは §2.3 の実装タスクで判断する。**推奨は新設**: 円弧のあらゆる利用箇所(`curveStart` / `curveEnd` / `arcPointAt` 等)が「1 つの半径」を前提にしているため、`ResolvedArc` を拡張すると全箇所の見直しが要り、新設のほうが影響範囲を閉じられる)。カーネルは `makeEllipseEdge.ts`(新規)。

**スプライン(FR-317):** 新しい `SketchFeatureKind` `'spline'`(`mode: 'interpolate' | 'control'`、点の参照配列 `readonly SketchPointRef[]` または直接の座標配列)。1 フィーチャー = 1 `ResolvedCurve`(新設 `ResolvedSpline`)。カーネルは `makeSplineEdge.ts`(新規、§0.17 のとおり `GeomAPI_PointsToBSpline` を使う)。表示用の折れ線化(`sampleCurve.ts` の拡張)は、B スプラインの解析形をカーネルから受け取れないため(P1〜P3 は model 側で解析的にサンプリングしているが、スプラインは model 側に曲線の数式が無い)、**面を張らない単体のスプラインの表示は、カーネルにサンプリング専用の依頼を 1 つ追加する**(`tessellateSketchFaces` と同じ Worker 往復だが、スプラインは面が無くても表示のたびに曲線の形を知る必要があるため。詳細は該当タスクで設計する)。

**円(中心+半径、FR-326)と 2 点+半径の円弧:** model の型変更は不要。円は既存の `arc` kind で `startAngle=0, endAngle=360`(`isFullCircle`)を作る UI 専用の 1 段の道具を新設するだけ。2 点+半径の円弧も、UI 側で中心を計算(§0.18)してから既存の `arc` を作る。

### 2.4 3D スケッチ(FR-330)

§0.4・§0.5 の決定に従い、新しい文書種は作らない。`SketchFeatureBase.planeId` の型を `WorkPlaneId`(§2.8 で `string` を許すよう拡張)に加え、3D スケッチであることを示す特別な値 `'free'` を予約する。`planeId === 'free'` のフィーチャーは:

- **点・線分:** `CoordinateInput` の absolute / relative モードをそのまま使う(§0.4 のとおり既に作図面非依存)。polar モードは UI から隠す(§0.5)。
- **円弧:** 作図面から法線・第 1 軸を借りられないため、`SketchArcFeature` に**その円弧専用の**法線・第 1 軸を持たせる(3 点通過、または「中心+法線ベクトル+開始方向」のいずれかで指定。UI の実装は該当タスクで決める)。
- **点の基準(`PointReference`):** §0.7 の決定により `{ kind: 'subShape'; ref: SubShapeRef }` を追加する。UI は「立体の頂点をクリックする」操作(§2.6)からこの参照を組み立てる。
- **面:** 3D スケッチの面(押し出しや面と面をつなぐ立体(P5、FR-430)の材料になる)は、境界の曲線が同一平面に乗っている限り既存の `makePlanarFace.ts` で作れる。**境界が同一平面に乗らない場合(3D スケッチでは「立体の 3 つ以上の頂点を結んで面を張る」が主な使い方になり、これはほぼ確実に非平面になる)は範囲外にできない。** 要件§9 の P4 完了条件が「3D スケッチで…立体の頂点から…面を作れ」と明記しており、これを平面の場合だけに限ると完了条件を満たせない。**`BRepFill_Filling`(2026-09-04 に実在確認済み。`constructor(Degree, NbPtsOnCur, NbIter, Anisotropie, Tol2d, Tol3d, TolAng, TolCurv, MaxDeg, MaxSegments)`、境界の辺を `Add_1(edge, order: GeomAbs_Shape, isBound)` で順に足し `Build()` → `IsDone()` → `Face()`。予備として `BRepOffsetAPI_MakeFilling` も同一引数構成で存在を確認済み、`Build(theRange: Message_ProgressRange)` が進捗引数を取る点だけ異なる)を用いる**。`Add_1` の `Order: GeomAbs_Shape` は列挙引数(§0.23 と同じ型ガードが要る可能性。値は位置だけ拘束する `GeomAbs_C0` を使う)。`resolveFace` は `isPlanar` の判定結果に応じて、平面なら従来どおり `makePlanarFace.ts`、非平面なら新設の `makeFilledFace.ts` を呼ぶよう `recomputeSketch` 側の橋渡しを分岐させる(タスク 10b)。

### 2.5 既存要素を参照する整形系道具

§0.10 の決定(トリム/延長/フィレット/面取りは書き換え、オフセット/ミラー/複写/配列複写は追加)に基づく。

**構築線(FR-320):** 新しい `SketchFeatureKind` は作らず、`SketchLineFeature` / `SketchArcFeature` / `SketchPointArrayFeature`(および §2.3 の矩形・正多角形・長穴・楕円)の各型へ `construction: boolean`(既定 `false`)を足す。`resolveFace` の境界解決で `construction: true` の要素は選べないようにする(境界の一覧を作る UI 側で除外する、または選んだ時点で `mixedBoundary` 相当のエラーにする)。表示は破線にする(`buildSketchGeometry.ts` / `createSketchLayer.ts` に「構築線」用の描画種別を足す。three.js の `LineDashedMaterial` を使う)。

**オフセット(FR-321):** 新しい `SketchFeatureKind` `'offset'`(`source: readonly SketchElementRef[]`(オフセット元の線・円弧・輪郭)、`distance: ExpressionValue`(符号で内側/外側))。原本は変えず、複製として履歴に積む(追加系)。カーネルは `makeOffsetWire.ts`(新規、`BRepOffsetAPI_MakeOffset`)。

**トリム・延長(FR-322):** model の型変更は、新設する `PointReference` の種類 `{ kind: 'intersection'; a: SketchElementRef; b: SketchElementRef }` のみ(§0.10)。トリムは「切る側の要素」の該当する端点の `CoordinateInput` を、この新しい参照+ `mode: 'relative', dx=dy=dz=0` へ書き換える(`sketchCommands.ts` の `continueFrom` と同型)。延長も同じ参照の仕組みを使い、伸ばす先の要素との交点を計算して端点を置き換える。UI 側は `attachSketchInteraction.ts` に「クリックした場所に最も近い、選んだ 2 要素の交点」を求める処理を追加する(`snapMath.ts` の `segmentIntersection` を曲線一般(直線×直線・直線×円弧・円弧×円弧)へ拡張する)。

**スケッチのフィレット・面取り(FR-323):** ハイブリッド実装(§0.10・§0.20)。2 本の線の共有する端点を、丸め・面取り後の新しい 2 端点へ書き換え、その間を埋める新しい `arc`(フィレット)または `line`(面取り)フィーチャーを 1 つ追加する。カーネルは `makeSketchFillet2d.ts` / `makeSketchChamfer2d.ts`(新規、`ChFi2d_FilletAlgo` / `ChFi2d_ChamferAPI`)。**この操作だけは model 側の Vec3 演算では完結せず、カーネル(Worker)への往復が要る**(円弧・接線の計算は OCCT に任せる)。

**ミラー・複写・配列複写(FR-324):** 新しい `SketchFeatureKind` `'mirror' | 'copy' | 'array'`。いずれも原本を変えず追加系。座標変換はカーネルを呼ばず model 内の `Vec3` 演算(§0.21)で行う。ミラーは基準線・基準面(3D スケッチなら任意の平面フィーチャー)に対する反射、複写は平行移動、配列複写は直線状(間隔+個数)または円形状(中心+角度+個数、P3 の `PatternPlacement` と同型)。

### 2.6 立体の部分形状の参照と、型の置き場の組み替え

§0.7 の決定に基づき、`SubShapeRef` / `SubShapeFingerprint` / `SubShapeKind` / `FaceSurfaceKind` / `EdgeCurveKind`(現状 `packages/model/src/part/types.ts`)と、`isSameSubShape` / `dedupeSubShapeRefs` / `subShapeKindOf` / `fingerprintKeyText`(現状 `packages/model/src/part/subShapeRef.ts`)を、新規 `packages/model/src/geometry/subShapeRef.ts` へ移す。`part/types.ts` はここから re-export する形にして、`part/*` の既存コード(`resolvePart.ts`・`kernelBridge.ts`・`createPartDocument.ts` 等)の import 文は変えずに済ませる(named import の解決先だけが変わる)。`model/index.ts` のバレル輸出の輸出元パスを更新する(輸出する名前の集合は変えない。**`@pointercad/model` を使う `packages/ui/**` の import 文は 1 つも変更不要**)。

`sketch/types.ts` の `PointReference` に `{ kind: 'subShape'; ref: SubShapeRef }` を追加する(§2.4)。`resolveCoordinate.ts` に 1 case を足し、`ref.fingerprint.position` を返す(ただし、この参照は**再計算のたびに指紋で選び直す必要がある**ため、実際にはスケッチ単体の `resolveSketch` では完結せず、`PartDocument` レベルの解決(`resolvePart.ts`)で「立体を解決した後に、それを参照するスケッチの `subShape` 参照を選び直す」処理が要る。§2.7 の遅延解決の仕組みと合流する)。

UI 側は 3D スケッチの「点」道具に、立体の頂点をクリックして選ぶモードを追加する(`selectionKind` を `'vertex'` にして既存の `pickSolidSubShape` をそのまま使う)。選んだ頂点から `SubShapeRef` を組み立てる関数(`subShapeRefOf`、`subShapeSelection.ts` に実装済み)をそのまま再利用する。

### 2.7 投影・交差(FR-325)と `PartDocument` の解決順序

§0.11 の決定に基づく、本計画で最もリスクが高い実装。

**文書の形:** 新しい `SketchFeatureKind` を 2 つ足す。`'projectedCurve'`(`source: SubShapeRef`(投影する面・辺)、`planeId`(投影先の平面))と `'planeSection'`(`targetFeatureId: string`(断面を取る立体)、`planeId`)。いずれも既存の `SubShapeRef` の指紋で再計算のたびに選び直す(§2.6 と同じ仕組み)。

**解決順序の組み替え:** `resolvePart.ts` の現状のメインループは、①全スケッチを独立に `resolveSketch` で解決し、②`document.solids` を順に解決する(ソリッドがスケッチの面・線・点を参照する)、の 2 段構成である。投影・交差フィーチャーを持つスケッチは、②の中で**そのフィーチャーが参照する立体が解決された直後**に遅延解決する必要がある。具体的には:

1. ①で全スケッチを解決する際、投影・交差フィーチャーは「まだ解決できない」ものとして `pending` の印を付け、`ResolvedSketch` には含めない(通常の `errors` とは別の扱いにする。この時点でエラー扱いにすると FR-504 の「止めずに警告する」の意図と違う一時的な状態になるため、専用のマーカーを設ける)。
2. ②のメインループが `document.solids` を 1 つ解決するたびに、「いま解決できるようになった投影・交差フィーチャー」(参照する `targetFeatureId` / `SubShapeRef.bodyFeatureId` がちょうど解決されたソリッドと一致するもの)があれば、その場でカーネル(`makeSection.ts` / `makeProjection.ts`)を呼んで解決し、結果の `ResolvedCurve` をそのスケッチの `ResolvedSketch` へマージする(`mergeProjectedCurves` のような関数を新設)。
3. マージ後のスケッチが**後続の**ソリッドフィーチャーの profile として参照されていれば、通常どおり使われる。

**制約(明文化して要件・ヘルプへ残す):** 投影・交差フィーチャーが参照できるのは「自分より前に `document.solids` へ出現するソリッド」だけで、後から出現するソリッドは参照できない。この制約は完了条件(「既存の立体の面・辺を投影して**次の**加工の下描きにできる」)を満たすには十分だが、循環参照(投影の結果を使って作った立体を、また別の投影が参照する)のような入り組んだ使い方は成立しない場合がある(その場合は `missingBody` 相当のエラーで断る)。

**カーネル:** `makeSection.ts`(新規、`BRepAlgoAPI_Section_5`)、`makeProjection.ts`(新規、`BRepProj_Projection_1/2`)。投影・交差の結果(`TopoDS_Wire` / `TopoDS_Compound`)を PointerCAD の `ResolvedCurve`(線分・円弧の列)へ変換する処理は、結果が直線・円弧だけとは限らない(自由曲線になり得る)ため、§1.4-5 の実測を経てから設計する。

### 2.8 任意の作業平面(FR-328)と基準軸/点/座標系(FR-329)

§0.13 の決定に基づき、`WorkPlaneId` を `'xy' | 'xz' | 'yz' | string` へ拡張する(文字列は任意平面フィーチャーの id)。`resolveSketch.ts` に、`feature.planeId` が固定 3 枚のいずれでもないとき、文書内の該当する `'referencePlane'` フィーチャーを探して `WorkPlane`(origin/axisU/axisV/normal)へ解決する経路を追加する。任意平面フィーチャーは解決前の他の任意平面を参照できない(先に定義されたものだけを参照できる、履歴順の制約。§2.7 と同じ考え方)。

- `'referencePlane'`: 3 点指定(`GC_MakePlane_6`)/ 面からのオフセット(`GC_MakePlane_5` 相当、model 側で計算)/ 辺を軸にした角度傾け(model 側で `gp_Ax1` 相当の回転を Vec3 演算で計算)の 3 通り。カーネルは呼ばない(model 内の Vec3 演算で完結する。§0.21 のミラーと同じ判断)。
- `'referenceAxis'`: 2 点、または点+方向。
- `'referencePoint'`: 既存の `CoordinateInput` をそのまま使う(実体は `SketchPointFeature` と同じだが、面の境界に使えない扱いにする。もしくは既存の点フィーチャーへ `role: 'reference'` の印を足すだけで済むかは実装タスクで判断する)。
- `'referenceCoordinateSystem'`: 原点+ 3 軸の向き(`referenceAxis` を 2 本、または `referencePlane` + 法線から第 3 軸を導く)。

`PlaneMenu`(`Toolbar.tsx`)は固定 3 枚に加えて文書内の任意平面フィーチャーの一覧を動的に表示する。表示/非表示は各フィーチャーの `visible: boolean` で切り替える(作図面の表示切替と同じ発想)。

### 2.9 失敗の扱い(FR-504、NFR-RE-1)

P1〜P3 と同じ方針を踏襲する。①解決の失敗(座標が求まらない、参照が見つからない)は `SketchError` として持ち回り、そのフィーチャー以降の参照先にしない。②カーネルの失敗(面が張れない、オフセット/フィレット/投影が不成立)は日本語の `Error` を投げ、`recomputeSketch` 相当の層で捕まえて `kernelFailed` 系のエラーへ変換する。③OCCT が異常終了する可能性がある操作(スケッチのフィレット・面取り、オフセット、投影・交差)は、P3 で入れた Worker 再起動の仕組み(`kernelBridge.ts`)がそのまま効く前提で設計する(新しい再起動の仕組みは作らない)。

## 4. 共通の作業規約(全タスク共通)

- **gitへ書き込まない。** 変更したファイルの一覧と検査結果を統括へ報告する(`rules/01-役割と委譲.md` §1)。
- **依存を勝手に足さない。** P4 で追加する外部依存は原則 **0 件**(§1)。文字の輪郭化(FR-319、Should)で新規依存が必要と判明した場合も、**作業を止めて統括へ提案**する(`rules/02-禁止事項.md`)。
- **`eslint-disable` / `@ts-ignore` / `@ts-expect-error` / `any` / `as` による強制変換で赤を消さない。** P3 で承認された `makeFillet.ts` の述語ガード以外に新しい抑止が要ると分かったら、**理由を添えて統括へ提案**する(承認前に書かない)。
- **テストの期待値を緩めない。** 実測が期待値と違ったら、値を書き換えるのではなく**実測値と自分で検算した値を統括へ報告**する。性能の上限値(500ms / 5000ms)も緩めない。
- **ブラウザの窓・Electron・開発サーバーを起動しない。** ヘッドレスのテスト実行(Vitest、Playwright の headless)は可。
- **`async` 関数に `await` が 1 つも無い形にしない**(`@typescript-eslint/require-await`)。
- **静的メソッドを値として渡さない**(`@typescript-eslint/unbound-method`)。
- **`switch` の各節を必ず `return` か `break` で閉じる**(`no-fallthrough`)。分岐が増えたら関数へ切り出す。
- **UI 文字列は `packages/ui/src/i18n/ja.json` に置く。** `.tsx` へ日本語を直書きしない(`i18n.test.ts` が機械的に落とす)。**並列で走っている相手が `ja.json` を触っていないことを確かめてから足し、報告に書く。**
- **OCCT で確保したものは必ず `delete()` する。** `packages/kernel/src/occt/allocations.ts` の `createAllocations()` を使い、`try` / `finally` で確実に呼ぶ。
- **`opencascade.full.d.ts` は巨大なので Read で全文を読まない。** 必要な宣言だけを Grep で確かめる。
- 検査は `pnpm run typecheck` / `pnpm run lint` / `pnpm run test` / `pnpm run build` の 4 つ、または `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.ps1 -Level Commit`。**並列で作業しているときは `scripts/check.ps1` を担当が実行しない**(他担当の途中コードで一過性に落ちるため)。自分のパッケージの `pnpm --filter <名> run test` で足りる。
- 各タスクの最後に、統括が `git diff` を読むための報告(変更ファイル、検査の実行コマンドと出力の要点、実測値)を出す。
- **機能を足したタスクは、同じタスクでヘルプとテストも足す**(`rules/04-設計の規律.md`、NFR-MA-4)。ヘルプは**利用者の操作と画面表示だけ**を書き、内部用語(B-rep、指紋、キャッシュ、Worker、トポロジー、テッセレーション)を出さない(`rules/05-リリース.md` §11.3)。
- **既存ファイルを変更する前に、そのファイルを Read して現在の内容を確かめる。** 計画書の記述と食い違っていたら**止めて統括へ報告**する。
- **変更ファイル数が 10 を超えそうなタスクは、着手前に統括へ相談する**(P3 の実績に合わせた目安)。

| `3 → ... → 10 → 15 → 17 → 18 → 20 → 25 → 27 → 32 → 33 → 34` | 13 |

**最長経路が P3(11 段)より長い**のは、P4 の機能どうしの依存が深い(新図形→3D スケッチ→編集系→投影/交差、という積み上げ構造)ためである。並列できる組(§6.4 に無いファイルの組み合わせ)を最大限使っても、この 15 段の鎖の長さ自体は縮まらない。

### 6.9 統括への確認事項

§0 に **24 件**。優先順位(依存が多く・後続への影響が大きい順):

1. **§0.4・§0.5(3D スケッチの文書表現)** ── タスク10・10b・14 のすべての前提。
2. **§0.7(`SubShapeRef` の移設)** ── タスク3・10・14 の前提。3 は他の多くのタスクの先行でもあり、依存方向の組み替えを含む最初の model タスク。
3. **§0.8(複数曲線を生む図形の型、`curvesByFeature`)** ── タスク4・5・6・7・8・11・12 のすべての前提。既存の `pickMath.ts` / `snapMath.ts` / `buildSketchGeometry.ts` への影響範囲が大きい。
4. **§0.10(履歴か書き換えか)・§0.11(投影・交差の解決順序)** ── タスク15〜27 の設計の骨格。特に §0.11 は本計画で最もリスクが高い判断で、タスク25 の着手可否を左右する。
5. **§0.1・§0.2・§0.3(表示テーマ・拡大率・設定の置き場)** ── 利用者の指示で最初の組として着手するため、他のどのタスクより先に承認が必要。
6. **§0.19(文字の輪郭化を含めるか)** ── タスク28〜30 の着手可否を左右する。実測(タスク28 手順1)を待たずに範囲外と決めてよければ、その 3 タスクを計画から外して工数を圧縮できる。
7. **§0.12(拘束をP4に含めるか)** ── 含めない前提で計画したため、含める場合は追加の計画が要る。
8. **§0.23(列挙引数への型ガードの追加使用)・§0.24(スキーマ版4)** ── タスク16・10b・31 の着手可否。
9. その他(§0.6、§0.9、§0.13〜§0.18、§0.20〜§0.22)は各タスクの着手前に個別に読み直せば足りる。

### 6.10 懸念(統括へ)

1. **最長経路が 15 段(P3 の 11 段より長い)。** P4 は「新図形→3D スケッチ→編集系(トリム/フィレット等)→投影/交差」という積み上げ構造で、各段が前段の型・関数を前提にするため、並列化の余地が P3 より小さい。所要時間の見積りに影響する。
2. **投影・交差(タスク25)は本計画で最もリスクが高い。** `resolvePart.ts`(1673 行)の解決順序そのものを組み替える設計で、既存の 200 フィーチャー規模の性能(NFR-PF-3)を壊さない実装が難しい可能性がある。実測で 5 秒を超えた場合、キャッシュ戦略の見直しなど追加の設計判断が要る。
3. **文字の輪郭化(FR-319)は §1.2 の事前調査の時点で疑わしい状態(`StdPrs_BRepFont` の実行時の挙動が未確認)。** タスク28 の手順1 で動かないと判明した場合、タスク28〜30 の 3 タスクを打ち切ることになる。**早期に統括の判断(§0.19)を得られれば、この 3 タスクを計画から外して工数を圧縮できる。**
4. **`curvesByFeature` の新設(§0.8)は P4 の全域に影響する構造変更である。** 既存の `sketch.segments` / `sketch.arcs` を「1 featureId = 1 curve」の前提で直接参照している箇所(`ui/src/sketch/pickMath.ts`・`snapMath.ts`・`buildSketchGeometry.ts` 等)をすべて洗い出して `elementId` ベースへ見直す必要があり、見落としがあると実行時にだけ現れる不具合(型検査を通るが動かない)になりうる。タスク4 の手順1 で Grep による洗い出しを徹底することが重要。
5. **スプラインの通過点方式(タスク8・11)は近似であり厳密な補間ではない。** 利用者が「点を通る曲線」を期待して作った形が、許容誤差の範囲内でわずかにズレる可能性がある。ヘルプ(タスク12)でこの性質を明記する設計にしたが、実際の見え方は統括の目視(§5.2)で確認が要る。
6. **ツールバーの再編(タスク32)を最後の 1 タスクへ集約したことで、それまでの機能タスク(4〜30)は UI から実際に使えない状態が続く。** P3 の教訓(共有ファイルの後半集約による直列化)を踏まえた設計判断だが、**動作確認が計画の終盤までできない**というトレードオフがある。統括が中間時点で目視確認したい場合は、タスク32 の一部(たとえば「作図」区画だけ)を早めのタスクとして切り出す判断もありうる。
7. **参照ジオメトリ(平面・軸・点・座標系)をスケッチの `SketchFeatureKind` として持つ設計(§0.13)は、スケッチ 1 本の中に「実体を持つ要素」と「参照専用の要素」が混在することになる。** 将来アセンブリ(P7)で座標系の扱いが必要になったとき、この設計が再利用できるかは未検討であり、P7 着手時に見直しの余地を残す。

## 7. P5 への申し送り

P4 で意図的に P5 以降へ送った点、および P5(基本形状・球面グリッド・面をつなぐ立体)が P4 の設計にどう乗るかをここへ残す。P4 のタスクにこれらの実装は 1 つも含めない。

| # | 何を残すか | 該当タスク | なぜ P4 で決めたか |
|---|---|---|---|
| (a) | `PointReference` を discriminated union のまま保ち、各 kind の解決を 1 関数 1 case に閉じる設計 | 全 model タスク | P5 で `{ kind: 'sphereGrid'; sphereFeatureId; latitude; longitude }` を足すだけで済むようにする(§0.6)。**型は P4 では足さない**(§0.6 の判断どおり)。 |
| (b) | `SubShapeRef` の中立な置き場(`packages/model/src/geometry/subShapeRef.ts`) | タスク 3 | P5 の基本形状(球等)や P7 のアセンブリが同じ部分形状の参照の仕組みを使う際、`part` からも `sketch` からも参照できる土台がすでにできている。 |
| (c) | 投影・交差の解決順序の仕組み(§2.7、`resolvePart.ts` のメインループへの割り込み) | タスク 25 | P5 の「面と面をつなぐ立体(罫線面、FR-430)」は、3D スケッチの点・線・面(P4 で作る)や球面グリッドの点(P5)を材料にする。3D スケッチのフィーチャーが立体を参照する経路が、逆に立体側のフィーチャーが 3D スケッチを参照する形として P5 でも再利用できる見込みだが、**設計そのものは P5 の計画時に判断する**。 |
| (d) | 表示テーマ・拡大率のトークン基盤(`--pcad-*`、`localStorage` の設定永続化) | タスク 1、2 | P5 の外観(FR-1106〜1110、材質プリセット・柄)は色・柄の個別設定であり、表示テーマとは独立した別の仕組みになる見込みだが、**設定の永続化の形(`localStorage` の 1 キーに JSON で持つ)は使い回せる**。 |
| (e) | 3D スケッチの円弧が専用の法線・第 1 軸を持てる形(`freeOrientation`) | タスク 10 | P5 の球面グリッドの交点(緯度・経度)から円弧・曲線を作るときも、作図面に依らない向きの持ち方として同じ仕組みが使える見込み。 |

**P4 の担当への注意:** 上記 (a)〜(e) 以外は P5 の設計に踏み込まない。球のフィーチャー・球面グリッド・面をつなぐ立体の実装は P4 のどのタスクにも含めない(§0.6 の判断どおり)。
