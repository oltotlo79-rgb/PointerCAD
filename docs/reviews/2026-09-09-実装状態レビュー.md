## 4. 修正を優先する指摘

優先度は作業順を示す。P1 は保存データ・寸法の正確性・入力による資源消費に関する優先修正、P2 は通常の品質改善として早期対応するもの。セキュリティ上の深刻度を数値評価した CVSS ではない。

### R01 — P1: 復元に失敗しても唯一のバックアップを消してしまう

**根拠:** [pcadDialogs.ts](../../apps/desktop/src/main/pcadDialogs.ts#L171) `writeBytesTo`、171–219行。

一時ファイルへの書き込み後、`rename` が失敗すると元ファイルを `.backup-*` へコピーする。その後の上書きが失敗し、195行および211行の復元も失敗した場合でも、217行でバックアップを削除する。

**再現:** 実際の保存入口へ、元データ `ORIGINAL` を持つメモリ上のファイルシステムを渡した。`rename` を失敗させ、上書きは `PARTIAL` を書いた後に失敗、バックアップからの復元も失敗させた。保存はエラーになったが、残ったのは `model.pcad = PARTIAL` だけで、元データ入りのバックアップは削除された。

**影響:** 多重の I/O 障害時に、ユーザーが後から回収できる最後の正常コピーまでアプリ自身が消す。通常保存の成功だけを検証しても見つからない。

**改善:** 「書き込み完了」「元へ復元済み」「復元不能」を分ける。正常保存または復元を確認できるまでバックアップを消さず、復元不能時は回収方法を伝える。バックアップ保持自体が失敗した場合も、元の原因を失わない結果にする。

**受入条件:** 置換失敗・部分書き込み・復元失敗・後始末失敗を組み合わせ、復元不能時に `ORIGINAL` のコピーが残ること。成功時には新しい内容が残ること。

### R02 — P1: 遅れて完了した保存が別文書の状態と自動保存を変更する

**根拠:** [partFile.ts](../../packages/ui/src/file/partFile.ts#L368) `savePart`、368–425行。[fileGateway.ts](../../packages/ui/src/file/fileGateway.ts#L765) 765–813行。

`savePart` は373行で文書 A を取り出し、388行で保存を待つ。完了後は現在の store を取り直し、文書 ID の照合なしに403行で A の保存状態を設定し、421–422行で現在の自動保存口へ `discard()` を呼ぶ。

**再現:** A の保存を Promise で保留し、その間に現在の文書を B に切り替えた。A の保存を完了すると、実コードは次の呼び出しを行った。

```text
setFileState: 現在 B / ファイル名 A.pcad / 保存済み文書 A
setFileMessage: 現在 B / file.saved
discard: 現在 B
discard: 現在 B（旧形式の控え用）
```

さらに実 browser gateway で `close()` を保留して `clearSaveTarget()` を呼ぶと、`hasSaveTarget()` は一度 false になるが、古い保存完了後に true へ戻った。793行の `saveTarget = target` がクリアを上書きする。

**影響:** 文書 B の名前・保存基準・復旧控えに、A の保存結果が混入する。保存先の寿命も切り替えに追従しない。実ストレージを消す実験はしていないが、破棄 API が別文書に対して呼ばれることを確認した。

**改善:** 保存開始時の文書 ID、世代、保存対象の版、自動保存の識別子を保持し、完了時に照合する。gateway も世代を持ち、古い完了が保存先を復活させないようにする。同じ文書へ保存中に追加編集した場合も、追加分の控えを削除しない。

近い既存実装として [assemblyFile.ts](../../packages/ui/src/file/assemblyFile.ts#L88) は97・102行で ID を確認し、110行では未保存変更を確認してから控えを削除する。この考え方を部品・アセンブリ・図面で共有すると、修正と今後の実装をまとめられる。ただし gateway 側の世代管理も必要である。

**受入条件:** 保存中の新規作成、別文書を開く、文書種別切替、同一文書の追加編集、複数保存の完了順逆転で、別文書の状態・保存先・控えが変わらないこと。

### R03 — P1: 「部品に戻る」で図面と履歴が破棄される

**根拠:** [DrawingWorkspace.tsx](../../packages/ui/src/drawing/DrawingWorkspace.tsx#L60) 60行、[drawingSlice.ts](../../packages/ui/src/store/drawingSlice.ts#L128) 128–136行、[attachAutoSave.ts](../../packages/ui/src/file/attachAutoSave.ts#L427) 427–431行。

戻るボタンは直接 `closeDrawing()` を呼ぶ。これは `createDrawingInitialState()` を適用し、図面、保存済み図面、図面の Undo 履歴を null に戻す。変更確認を通らず、図面の自動保存口も現在は接続されていない。

**再現:** drawing slice で図面を開いて寸法を追加すると、図面が存在し、図面履歴は1件になる。`closeDrawing()` 後は `drawing = null`、`drawingUndoStack = null`、元の部品履歴が空なら `canUndo = false` となった。

**影響:** 現在公開されている図面編集操作で作った内容が、通常の戻る操作で store から消え、通常の Undo でも回収できない。

**改善:** 文書を閉じずに切り替えるなら図面セッションを保持する。閉じる操作なら既存の未保存保護と保存・復旧経路へ接続する。保存未接続の段階でも、何も案内せず編集内容を破棄する操作にはしない。

**段階の区別:** 図面保存の後段接続が予定されていることは承知している。ここで指摘するのは将来機能の未実装件数ではなく、現在動く編集 UI に存在する破棄経路である。

### R04 — P1: 正確に求めたパラメーター値を、文書反映で丸め直して別の値にする

**根拠:** [parameterTable.ts](../../packages/model/src/parameters/parameterTable.ts#L139) 139–169行、[reevaluatePart.ts](../../packages/model/src/part/reevaluatePart.ts#L573) 573–604・652–671行。

依存解析は `exactVariables` を使って Decimal の十進表記を次へ渡す。しかし返す解析結果は `Map<string, number>` だけで、`applyParameters` はその number 表だけを使って文書とパラメーター自身を再評価する。

**実コードの出力:**

| 入力 | 依存解析の結果 | 文書に反映された結果 |
|---|---|---|
| `a=1/7; b=7*a-1` | `b = 0` | `b = -5e-17` |
| `a=1/7; b=(7*a-1)*1000000000` | `b = 0` | `b = -5e-8` |
| `a=10000000000000000; b=a+1; c=b-a` | `c = 1` | `c = 0` |

全て `analysis.failures` と文書再評価の `failures` は空だった。巨大な値の例は差を明確に示すためのもので、通常寸法で同じ大きさの誤差が出ると主張するものではない。`1/7` の通常の式でも結果の不一致は成立する。

**影響:** パラメーター表の解析値、保存される `ExpressionValue`、それを参照する形状側で、一貫した数値を使えない。最終段だけで丸めるという NFR-RE-4 の狙いが境界で崩れている。

**改善:** 解析結果に正確な十進表記を保持し、文書の式評価まで同じ評価コンテキストを渡す。表自身の値を不正確な変数表から重ねて計算しない。number が必要な公開境界でのみ丸める。

**受入条件:** `analyzeParameters` 単体だけでなく `applyParameters` の後まで、解析値・文書値・表示値の契約が一致すること。[既存テスト](../../packages/model/src/parameters/parameterTable.test.ts#L63) の精度検証を反映経路まで拡張する。

### R05 — P1: 無次元パラメーターを含む inch 式がプレビューと再計算で異なる

**根拠:** [ParameterPanel.tsx](../../packages/ui/src/parameters/ParameterPanel.tsx#L196) 196–199行、[length.ts](../../packages/model/src/units/length.ts#L217) 217–236行、[parameterTable.ts](../../packages/model/src/parameters/parameterTable.ts#L154) 154行、[reevaluatePart.ts](../../packages/model/src/part/reevaluatePart.ts#L578) 578行。

UI は角度・無次元の名前を `nonLengthVariables` として渡す。式エンジンは、この集合にない変数を単位付き式内で長さとみなす。ところがパラメーター依存解析と部品再評価はこの集合を渡していない。

**再現:** `n=2`、`unit='none'` とし、長さの式を `(n*1)in` にする。

```text
evaluateExpression（UI と同じ nonLengthVariables を指定）: 50.8
applyParameters の analysis.variables.L:                 2
applyParameters 後の L.value:                            2
```

**影響:** 計算不能のエラーにはならず、50.8 mm と2 mmという異なる寸法が正常な結果として扱われる。

**改善:** R04 と同じ共通評価コンテキストに、正確な値と非長さ変数の集合を含める。入力プレビュー、依存解析、部品再評価、保存後の再読込で同じ規則を使う。`ParameterUnit` の「表示だけ」という古いコメントも、実際の `nonLengthVariables` の利用と整合させる。

**受入条件:** mm・inch と、長さ・角度・無次元の組合せについて、プレビューと確定後の値が一致すること。既存 [length.test.ts](../../packages/model/src/units/length.test.ts#L286) の単体検証だけで完了にしない。

### R06 — P1: ZIP 展開上限は、制限を超えるデータが確保された後に判定される

**根拠:** [readArchive.ts](../../packages/io/src/pcad/readArchive.ts#L129) 129–163行、[limits.ts](../../packages/io/src/limits.ts#L22) 22–28行。

`file.ondata` に届いた `chunk.byteLength` を加算して制限するが、chunk は既に展開済みである。入力全体を `unzip.push(bytes, true)` へ渡しており、fflate の同期展開が巨大な出力を生成する前には止められていない。

**再現:** 2,000,000バイトの反復データを実際の fflate で ZIP 化すると2,083バイトになった。1エントリの上限を1,024バイトとして実 `readArchive` を呼び、`UnzipInflate` の出力コールバックを観測すると、最初に届いた展開済み chunk は **2,000,000バイト**。最終結果は正しく `entryExpanded` のエラーだが、その前に上限超過のデータが生成されていた。

**影響:** 圧縮ファイルのサイズ制限と「エラーになる」テストだけでは、メモリ枯渇対策を保証できない。今回確認したのは上限適用前の大きな出力であり、最大入力でのクラッシュや任意コード実行を確認したものではない。

**改善:** 展開器の出力確保前に残り予算を適用できる仕組みにする。圧縮データを小分けに渡すだけで十分かは、最大膨張量も含めて検証する。重い解析を Worker に分離し取消可能にする対策は応答性を助けるが、それ自体はメモリ上限の保証にはならない。

**受入条件:** 最終的に `ok:false` となることに加え、展開途中に生成・保持するデータの最大量が定義した予算内であること。[既存テスト](../../packages/io/src/pcad/readArchive.test.ts#L87) は主に最終的な拒否を検証している。

### R07 — P2: Web は読み込み前にファイルサイズを確認しない

**根拠:** [fileGateway.ts](../../packages/ui/src/file/fileGateway.ts#L326) の `ReadableFile`、534–566・632–636・751–755行。Desktop の [pcadDialogs.ts](../../apps/desktop/src/main/pcadDialogs.ts#L139) 139–145行との比較。

Desktop は `stat.size` を読み、256 MiB を超える入力を `readFile` 前に断る。一方 Web は `File.size` をインターフェースで要求せず、picker と input の経路で `arrayBuffer()` を先に呼ぶ。

**再現:** `size=300*1024*1024` を持つ File 相当を picker から返すと、`arrayBuffer()` が1回呼ばれ、gateway は結果を返した。この実験は呼び出し順の検証であり、実際に300 MiBを確保したものではない。

**改善:** `File.size` の有限・非負・安全な整数と形式別上限を取得前に確認する。ストリーム読み取りにも実バイト数の制限を設ける。`.pcad` だけでなく型付きファイルの入口と input フォールバックを同じ検証へ集約する。

**受入条件:** 上限超過時の `arrayBuffer` 呼び出しは0回。上限ちょうど、空、メタデータ不正、フォールバック経路を検証する。

### R08 — P2: 数式の「成功」結果に Infinity が入る

**根拠:** [evaluateExpression.ts](../../packages/expression/src/evaluateExpression.ts#L55) 55–65行、[evaluate.ts](../../packages/expression/src/evaluate.ts#L325) 325–340行。

Decimal の有限性を確認した後で `toNumber()` するため、Decimal として有限でも JavaScript number の範囲外なら Infinity になる。

```text
evaluateExpression('10^309'):  ok=true, value=Infinity, display='1e+309'
evaluateExpression('10^1000'): ok=true, value=Infinity
evaluateExpression('1/0'):     ok=false, divisionByZero
```

**影響:** 成功結果は有限の数値という前提を破る。パラメーター依存解析は `ok` だけを見て値を変数表へ入れる。すべての UI や OCCT の入口が Infinity を受け入れるとまでは確認していない。

**改善:** number の公開直前にも `Number.isFinite` を適用する。正確な中間値を保持する内部表と、有限 number が必須の公開値を区別し、範囲外を明示的な評価失敗として返す。

**受入条件:** `10^308` 付近の有効値と `10^309` の範囲外を、通常評価・exact 評価・パラメーター適用まで確認する。

### R09 — P2: 図面 JSON が非有限値と無効な縮尺を受理する

**根拠:** [drawingJson.ts](../../packages/io/src/pcad/drawingJson.ts#L301) 301–327・375–406・537–545行。

`hasNumber`、点、ベクトル、縮尺の判定が `typeof value === 'number'` に留まる。JSON の `1e309` は構文上有効で、JavaScript の `JSON.parse` 後は Infinity になる。

**再現:** schema 9 の有効な図面封筒で `sheet.scale` だけを変えて `parseDrawing` へ渡した。

| JSON の scale | parseDrawing | 取り込まれた値 |
|---|---|---|
| `1` | 成功 | `1` |
| `0` | 成功 | `0` |
| `-1` | 成功 | `-1` |
| `1e309` | 成功 | `Infinity` |

**影響:** 読み込み時の検証済み文書として、描画・変換に不適切な縮尺を後段へ渡す。画面クラッシュを実機で確認したという指摘ではない。

**改善:** 有限数、正の縮尺、非負の幅、適切なベクトルという制約を欄ごとに定義し、共通ガードへまとめる。未知の欄を保持する前方互換と、既知の欄の妥当性検証は両立させる。

**受入条件:** 0・負数・範囲外指数・不正ベクトルは必要な箇所で拒否し、利用者に欄と理由を返す。現在の P8-64 は最後の監査であり、各型追加時に serde を足すという計画の訂正も守る。

### R10 — P2: ZIP の CRC 不一致を検出しない

**根拠:** [readArchive.ts](../../packages/io/src/pcad/readArchive.ts#L100) 100–178行。内容の展開・名前・件数は検証するが、エントリ内容と CRC の整合検査がない。

**再現:** fflate で非圧縮 ZIP を作り、`document.json` の `{"length":20}` の `2` を `9` に変更した。CRC フィールドを変更しないまま実 `readArchive` へ渡すと `ok=true`、内容は `{"length":90}` となった。

**影響:** ZIP としての偶発的破損を検出できない。JSON の構文と型が保たれた変更は、それらの検査だけでは分からない。

**改善:** 展開時に CRC-32 を計算し、記録された値との不一致をエラーにする。CRC は偶発的破損の検出であり、悪意ある改ざんに対する署名・真正性の保証としては扱わない。

**受入条件:** 元の ZIP は成功し、内容だけを変えた ZIP は失敗する。圧縮あり・なし、データディスクリプターを使う形式も対象にする。

## 5. セキュリティ・検証・保守の改善事項

### R11 — P2: CSP と Electron の明示的な権限拒否がない

**根拠:** [Web HTML](../../apps/web/index.html)、[Desktop HTML](../../apps/desktop/index.html)、[Web の配信ヘッダー](../../apps/web/public/_headers)、[appProtocol.ts](../../apps/desktop/src/main/appProtocol.ts#L46)。確認した配信・HTML 設定には CSP がない。apps 内で `setPermissionRequestHandler` / `setPermissionCheckHandler` の設定も見つからなかった。

COOP/COEP はプロセス・リソースの分離を助けるが、読み込める script や接続先を制限する CSP の代わりにはならない。Electron の公式ガイドも CSP と権限要求の処理を勧め、権限要求を処理しない場合の既定許可について説明している。[Electron Security](https://www.electronjs.org/docs/latest/tutorial/security)

**改善:** 実際に必要なローカルリソース、Worker、WASM、画像、印刷の経路を列挙して CSP を設定する。製品が使わないブラウザー権限は main の session で拒否する。開発用の例外を本番へ持ち込まない。

**評価の限界:** 現在成立する XSS・端末情報の取得・外部送信を確認したものではない。配信事業者側で追加される未確認の設定についても断定しない。ここでは、リポジトリにある防御設定の不足として扱う。

### R12 — P2: Desktop と Firefox が通常の自動検査範囲に入っていない

**根拠:** [Desktop package.json](../../apps/desktop/package.json) にテスト入口がなく、既存テストから main の保存・IPC・protocol の入口を直接検査する接続を確認できない。[Playwright 設定](../../e2e/playwright.config.ts#L24) の2 project はともに `Desktop Chrome` を継承する。

要件は Windows/Linux Desktop と Chrome/Edge/Firefox を対象にしている。OS の CI マトリクスは良いが、それだけでは Electron の実行時挙動や Firefox のファイル操作を検査したことにはならない。報告記録にある過去の手動 Desktop 確認も、継続的に実行される回帰検査とは別である。

**改善:** まず R01/R02 と送信元検証を、FS・dialog・IPC を注入できる小さな単体検査へ追加する。その後、Electron の起動・開く・保存・異常時保持の smoke と、Firefox の主要操作・ファイルフォールバックの E2E を通常の検査へ接続する。

**計測の区別:** スナップショット内にはテスト TS/TSX が389ファイルあり、そのうち E2E spec は19ファイルある。これはケース数でもカバレッジでもない。今回、行・分岐カバレッジを計測していないため、百分率を付けていない。

### R13 — P2: 検査前から変更済みのファイルがさらに書き換わっても検出できない

**根拠:** [gitTreeGuard.ps1](../../scripts/lib/gitTreeGuard.ps1#L119) 119–160行、[check.ps1](../../scripts/check.ps1) の Push 前後比較。

Push のスナップショットは `git status --porcelain --untracked-files=no` の文字列だけを保持し、159行で前後の文字列を比較する。開始時も終了時も ` M existing.ts` なら、内容が変わっていても同一と判定される。

**影響:** 「検査が追跡ファイルを書き換えたら失敗」という目的を、変更済みファイルに対して満たせない。今回、そのような書き換えを行う製品テストを発見したという意味ではない。

**改善:** 状態の集合だけでなく内容の指紋を比較する。開始時から変更済みのファイルも対象にし、削除・追加・改名も判定する。既存の fingerprint 関数を利用できる。

**受入条件:** clean→変更に加え、変更済み A→別内容 B が検出されること。実リポジトリへ書き込まない一時的な試験用リポジトリで検証する。

## 7. より速く、手戻りを減らして実装する提案

### 7.1 現物から分かった時間のかかる構造

1. **全検査の重複は運用として要求されている。** [rules/03](../../rules/03-品質ゲート.md) では統括の手動 Push 5段、pre-commit 4段、pre-push 5段を要求する。変更がない場合でも、型・lint・単体・build は各3回、E2E は各2回となり、その後に CI が加わる。各段を T/L/U/B/E とすれば、基本コストは `3×(T+L+U+B)+2×E`。今回は各段を同じ条件で測定していないため、削減分を何分・何%とは断言しない。
2. **失敗が終盤に出ると、必要な検証の再実行が増える。** 報告記録の19:18には、先行する検査成功後に格子性能が2ms上限を超過し、push が止まった事実がある。原因を CPU 競合だけと断定してはいけない。調査中に追加された rules/06 §10.44 は、初回時間と固定準備後の定常時間を分けて記録する方針を既に定めている。
3. **E2E の呼び出しごとに Web を組み立てる。** [playwright.config.ts](../../e2e/playwright.config.ts#L50) の `webServer.command` に build があり、E2E 連続実行でもその都度実行される。ただしこれは `VITE_PCAD_E2E=1` の検査用ビルドである。[PointerCadApp.tsx](../../packages/ui/src/app/PointerCadApp.tsx#L111) に専用の口があるため、通常の製品ビルドと同じ成果物だとみなして単純に省略できない。
4. **多数のタスクが同じファイルへ集まる。** P8 の UI 接続は `PropertyPanel.tsx`、`ja.json`、ツールバー、保存 codec に集中し、これらは既に大きい。番号単位で都度契約を作ると、後で境界を揃える作業が発生する。R02・R04・R05 は、その不一致が実際の不具合になった例である。

特に **P8-64 を前倒しで完了扱いにはしない**。計画の3284行は既に「各型変更時に保存・移行・往復検査を追加し、64は最後の監査」と訂正されている。これを実際の各作業へ適用することが、後半の入出力手戻りを減らす方法になる。

### 7.3 一つの作業束の進め方

1. **編集前に共通部分を一度だけ確認する。** 現在の SHA、既存変更、実在する関数・型、触れるファイル、先行条件、合格数値を指示書へ固定する。P8計画中の旧パスや旧型名をそのまま新規実装しない。
2. **最初に小さな一連の操作をつなぐ。** 例えば「注記1個を作る→表示→移動→Undo→保存→再読込」。正常系だけでなく、取消と不正入力も同じ契約へ置く。これで層ごとの実装が最後まで接続できない状態を早く発見する。
3. **共通処理の上へ種類を追加する。** PDF/DXFの違い、表の種類、プロパティ項目を、既存の型付き共用部に追加する。同じ評価・書式・保存コードを UI 側へコピーしない。
4. **開発中は対象診断を使う。** 既存の `-UnitPackage/-UnitTests` と `-E2EOnly/-E2EGrep` は、原因が局所化している修正の短い確認に使える。これらの成功を最終ゲートの合格としては扱わない。E2E/アプリの起動は規約どおり統括が行う。
5. **最後に束の全体検査へ進む。** 同じソースで成功した対象検査を、理由なく途中で繰り返さない。統合変更・失敗・未解決の懸念が出たときに再検証する。現行で必須の統括確認・フック・CIは維持する。
6. **完了報告は結果に対応づける。** タスクID、変更した公開動作、対象ファイル、実行した検査、未実施項目を短い表にする。テスト追加数や下書き作成を完成件数へ置き換えない。

この手順は子エージェントの増員を前提にしない。同じ変更点を複数の担当が編集することも避ける。

### 7.4 検証を速くする、具体的な改善候補

| 提案 | 削減する処理・手戻り | 守る条件・適用判断 |
|---|---|---|
| ゲート各段の時間を構造化して記録 | 実装時間・検査時間・失敗後の再実行時間を区別し、律速でない箇所の最適化を避ける | `check.ps1` の各段、SHA/内容hash、OS、厳密性能モード、終了コードを記録。まず複数回の実測を得る |
| 同一入力の E2E 用ビルドを連続検査で再利用 | `E2ERepeats` ごとの同じ Web build | 通常製品ビルドと E2E 用ビルドを区別する。ソース、lockfile、設定、`VITE_PCAD_E2E` 等の入力が一致しないときは再構築。ブラウザー状態とケースの初期化は毎回行う |
| 検査専用の共通 fixture・入口を整える | 保存・文書切替の異常系を、大きな実アプリ起動なしで診断 | R01/R02 のように FS・保存完了を制御する。純粋関数の代替実装だけをテストせず、本物の入口を通す |

| 巨大ファイルの「今触る境界」だけを切り出す | 同じ API や数値ガードを繰り返し探し直す作業、接続漏れ | R14 の責務に沿う。機能追加と無関係な全体再編は同じ束に混ぜない |
| 合格条件をシナリオ表へまとめる | 各タスクで似た正常系だけを増やし、境界異常系を見落とすこと | 正常、取消、範囲外、旧版、同時操作、文書種別の列を作る。既存の必要テスト数と閾値は維持する |

E2E用成果物の再利用はコード変更を伴う提案であり、今回実装していない。古い dist や稼働中の別サーバーを無条件に再利用する案ではない。

### 7.5 規約変更を伴う場合だけ検討する大きな短縮

**手動・pre-commit・pre-push で同じ結果を再利用する設計**には、前記の重複コストを減らす余地がある。ただし [rules/03](../../rules/03-品質ゲート.md) §7 が統括による再実行を明示的に要求している。現行のまま省略してよいという提案ではない。

変更するなら、単なる「直前に成功した」というフラグでは不十分で、少なくとも次を証明する記録が必要になる。

- 検査対象のファイル内容、staged 内容、lockfile、検査設定と実行コマンドが一致していること。
- OS、Node/pnpm、環境変数、性能の厳密モード、対象全ケース、終了コードが記録されること。
- 部分診断、古い結果、異なる成果物、欠けた記録は合格として受け付けないこと。
- 統括の差分レビューと、Windows/Linux CI を維持すること。
- 内容が変わったときは必要な全体検証を再実行すること。R13 の status 比較だけでは再利用判定に足りない。

独立した再実行による確認をどこまで残すかは、規約と監督方法の設計判断になる。今回は規約を編集せず、採用を前提にした時間見積もりも出していない。
