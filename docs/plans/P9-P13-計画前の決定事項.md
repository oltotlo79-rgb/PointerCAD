# P9〜P13 計画前の決定事項

## 0. 目的

本書は、P9〜P13 の各計画書を書く**最初の作業で埋める契約**を一か所にまとめる。レビュー 2026-09-07 の R8・R11-3・R12-3・R13-4を反映し、古い行数・schema版・目録数を実装の期待値として固定しない。

各計画の先頭には、次を混ぜずに置く。

| 区分 | 記録すること |
|---|---|
| 確認済み基準 commit | 計画作成時に読み直した commit、対象ファイル、実測した現在値 |
| 確定契約 | 利用者・統括が決定済みで、再承認を求めない設計 |
| 未実証 API | 型の存在だけでなく、実行時の存在・意味・所有権・失敗経路を確かめる項目 |
| 利用者未決 | 機能の意味・費用・運用・追加依存を変える選択。§6の決定へのリンクを持つ |
| 受入済み例外 | 規約・要件に対して承認済みの差と、その根拠・受入条件 |

各 FR には、`実装 / 保存移行 / Undo / 派生 cache / 選択 / 各出力 / エラー / 性能 / help / 検査` の該当タスクを1行で割り当てる。該当しない列も空欄にせず、対象外の理由を書く。古い章の推奨文より各計画の確定契約を優先し、未決一覧は消さず、決定記録へのリンクへ更新する。

## 1. P9 幾何公差（R8-1）

`packages/model/src/drawing/gdt.ts` に文字列でなく意味を持つ AST（`DatumId / ToleranceCharacteristic / ToleranceZone / FrameSegment[] / DatumReference[]`）を置く。

```ts
DatumId
ToleranceCharacteristic
ToleranceZone
FrameSegment[]
DatumReference[]
```

`packages/drawing/src/gdt/frameGeometry.ts` は区画を紙上寸法で組み、字体の欠字に依存する幾何記号をコードの vector 形状で描く。これは図示の支援であり、製品形状が公差へ適合するかの判定は行わない。

計画前に決めること:

- 採用する JIS の番号・年と14種の対応。
- 記号ごとに必要な datum、許す修飾、複合枠の範囲。
- datum が参照する面・軸等と、未解決参照の扱い。
- 溶接記号の体系と Must / Should の境界。
- DXFでの枠・記号・datumの表現。

最初の受入は規格表・AST・代表枠3種とし、P8のIR確定後に着手する。

## 2. P10 板金（R8-2）

`model/sheetMetal/` に、中立面を構成する平面パネルと円筒曲げのグラフ、固定面、内半径 `R`、曲げ角 `θ`、K係数、板厚 `t`、リリーフを保存する。Offset APIだけで展開せず、平面は剛体展開、円筒は中立面の周長へ写す。

曲げ長と曲げ控除は次を正本候補とし、`θ` は rad とする。

```text
BA=|θ|·(R+K·t)
BD=2(R+t)tan(|θ|/2)−BA
```

計画前に決めること:

- 一定厚に限定するか、初版で対応する曲げ種。
- Kの既定値と入力方法、材料・厚さ・加工条件の表を使うか（利用者判断）。
- 曲げ角の正負・基準面と、内寸 / 外寸のどちらを寸法基準にするか。
- 最小内R、最小フランジ長、リリーフの形と寸法。
- 閉ループの継ぎ目と、展開図の bend layer / 元形状参照。

実証順は直角L板 → U板 → 穴が曲げ近傍にある板とする。`BRepOffsetAPI_MakeOffsetShape` / `MakeThickSolid` は厚み生成の候補として実証するが、中立軸やKを自動計算するものとは扱わない。

## 3. P11 スクリプト（R8-3）

第一候補は、専用 Worker 内の組込み JavaScript VM とする。ネットワーク・FS・DOM・Electron を host binding として出さない。Workerに置くだけ、またはグローバル変数を消すだけを隔離境界とはしない。

QuickJS系を選ぶ場合は、採用 wrapper が次に相当する口を実際に露出するかを先行実証する。

```text
JS_SetMemoryLimit
JS_SetMaxStackSize
JS_SetInterruptHandler
```

CAD API は生の Zustand / Comlink remote / TopoDS / パスを渡さず、命令列と不透明IDだけを返す。命令列を検証後、文書へ1回のUndo単位で原子的に commit する。

計画前に決めること:

- VM / 別 origin 等の隔離方式（利用者判断）。
- メモリ、stack、実行時間、命令数、CAD命令数の上限。
- 非同期CAD呼出しと、途中失敗・timeout時の原子的適用。
- 乱数・時刻の決定性。
- CAD APIの版、scriptの保存場所、道具登録の保存と移行。
- import可能範囲と、行番号・source mapを保つエラー契約。

## 4. P12 ヘルプ・PWA（R8-4）

P12計画の先頭にFR別の対応表を置き、少なくとも `FR-508 / FR-509 / FR-911` を落とさない。全機能help本文は各機能で完成させ、P12は生成基盤・整合・仕上げを閉じる。

help目録 → 章 → 索引 → PDFを一つの manifest から生成する。撮影台本は fixture・カメラ・ダークテーマ・UI倍率・完了世代を固定し、撮影実行は統括の直列工程にする。

PWAは同じ `buildId` の JS / Worker / WASM / font を一組でcacheする。更新時はdirty文書を保持し、次回起動へ適用する。旧cacheは利用中clientが無くなってから破棄する。FR-509は利用者が選ぶ二文書 / スナップショットの比較であり、版管理を再導入しない。

計画前に決めること:

- オフライン利用の準備完了をどの時点とするか（利用者判断）。
- cache更新、容量不足、旧cacheからの復元。
- 説明書のPDF / HTML出力方式と配布物への収録。
- 画像のfixture・カメラ・テーマ・UI倍率・完了世代。
- 二文書差分の比較単位と、形状差の色分け。
- 履歴段のメモ・フォルダの保存とUndo上の意味。

## 5. P13 配布（R8-5・R8-6・R12-3・R11-3）

2026-09-09の利用者指示により、利用者向けREADMEの特徴・強み・機能紹介と、正式公開後の配布・説明書・Web版への導線を公開の完了条件へ含める。正本は[`rules/05-リリース.md` §11.1〜11.2](../../rules/05-リリース.md)とし、P13の計画・公開前検査・公開先確認へ必ず組み込む。

Cloudflare Pages の単一資産25 MiB制限に対し、`packages/kernel/src/occt/loadOcct.browser.ts:47-59` が使う約50.3 MBのWASMは現状のままでは配布できない。補修R-12で方式A（圧縮資産または各25 MiB未満のchunk + manifest/hash）を先行実証し、実サイズ・復元速度・一時メモリ・glueへの受渡しを測る。方式B（同じ管理者のR2等へWASMを分離）は、その実測後の利用者判断とする。ブラウザの自動Content-Encoding解凍と明示解凍を二重にしない。

desktopは検査済みcommitのversionを固定し、electron-builderで `pack → unpack資産確認 → 署名 → hash → release` の一方向へ流す。renderer / WASM / font / help / manual / NOTICEを同じ成果物として扱う。更新を採る場合も、作業中に強制再起動せず、署名・checksum・発行元を検証する。

CSPはWASM評価に必要な許可と一般JavaScriptのevalを分け、P11の隔離環境だけの例外を本体へ広げない。R2等へ分ける場合はCORS / CORP / Content-Typeを確認する。Dependabot等でnpmとActionsの更新提案を管理し、Actionsは検証済みcommit SHAへ固定する。releaseにはSBOM / NOTICEとOCCT / WASM / fontの版・hashを添える。

起動時間は `shell表示 / 操作可能 / WASM準備` の三点を別々に計測し、NFR-PF-5が指す時点を統括が固定する。E2Eの60秒待ちを起動要件の合格とは扱わない。

計画前に決めること:

- 対象OS / CPUと、各OSのインストーラ形式。
- 証明書・署名資格の主体（利用者）。
- 更新の有無、利用者へ同意を求める時機（利用者判断）。
- release channelと、旧版schema / 未来版控えの保全。
- GitHubのrelease・Actions・Pagesに必要な権限。
- 取扱説明書をWeb / desktopのどこへ同梱するか。
