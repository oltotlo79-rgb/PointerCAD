### 9.1 規約の構成と優先の順

- 「本書」は CLAUDE.md と rules/ の 7 文書。作業の前に全部読む。優先は「利用者の明示指示 > rules/ > CLAUDE.md」。同じ規約は 1 か所にだけ書く。

### 9.2 設計の規律（rules/04 の全項目）

1. **幾何の計算は double と明示の許容誤差。** 厳密な値（√・分数・π・累乗）を扱うのは `packages/expression` の中だけ。式は文字列のまま保存し、評価は任意精度、カーネル（OCCT）へは double に丸めて渡す（FR-202/203）。厳密演算を幾何と描画の全体に広げない。
2. **止めずに警告する。** フィーチャーの再計算の失敗（フィレットの不成立など）で落とさず、操作を塞ぐ関門も作らない。エラーの所を履歴の木に示し、直すか取り消すかを促す（FR-504、NFR-RE-1）。
3. **画面の状態は Zustand のストア 1 本に一元化する。** コンポーネントの useState は、ホバーなど表示だけの一時の状態にだけ使う。
4. **パッケージの依存の向きは一方向。** `apps → ui → model → kernel / expression / drawing` と `ui → fem → model`。FEM は model を使う計算の層で、model から FEM、FEM から ui・apps・io・help-content への依存は型だけでも禁止。drawing は kernel・model・ui・io に依存しない葉。UI から幾何カーネルへ直接依存しない。逆流や横流しは設計の欠陥として直す（NFR-MA-1）。
5. **純数値の共有は決まった入口だけ。** model の `kernelBridge/splineMath.ts` だけが `@pointercad/kernel/math/spline-interpolation` を、`kernelBridge/vectorMath.ts` だけが `@pointercad/kernel/math/vector-arithmetic` を参照できる。ほかの道から kernel の実行処理を借りない。
6. **幾何カーネルは Web Worker の中で動かす。** UI のスレッドで幾何の計算をしない。計算の間も進みの表示と取り消しが効くこと（NFR-PF-4）。
7. **導出できる物は保存しない。** `.pcad` に保存するのは、フィーチャーの履歴・式・拘束・図面の定義だけ。B-rep やメッシュは再計算で作る。
8. **説明を読まなくても触れる UI。** NFR-UX-1〜7 を全部の道具で守る。固定の区画（ツールバー・ツリー・ビューポートとビューキューブ・プロパティ・ステータスバー）を増やさない。
9. **機能を足す時は、ヘルプと検査を同時に足す**（FR-901、NFR-MA-4）。ヘルプに無い機能は公開に含めない。ただし利用者の指示で、**説明書とヘルプの本文・画像の書き直しは最後**（機能が固まった後にまとめて）。途中の版では、検査（controlInventory など）が求める最小の説明だけを足す。
10. **Web 版とデスクトップ版に機能の差を作らない。** 機種ごとのコードは `apps/` の下だけ。（3D マウスの機器の許可は、利用者の回答による、デスクトップ版だけの例外。）
11. **画面の文字は全部リソース（ja.json）に分ける**（NFR-MA-5）。コンポーネントに直書きしない（検査 i18n.test・jaMessages.test が見張る）。

### 9.3 このセッションで決まった実装の方針（規格部品・フレーム・操作）

- **規格部品（鋼材・アルミフレーム・機械要素）は同じ流れ**で扱う: 選ぶ窓 → 配置 → 部品表と切断の一覧に出る。族（family）ごとに、行の表（寸法）・形を作る関数・線図・registry・i18n・選ぶ画面の説明・照らす側の検査を揃える。
- **寸法の行は道具で作る**（手で打たない）。読みの表（2 つの独立の読み）→ 照らし合わせ → 一致した行だけ → 行のファイル。行ごとに出どころ（資料の番号・頁・表か図）を手元の記録に持つ。製品のファイルには出どころの名前を書かない。
- **形が足りない時は印で明示する。** 例: 「外形を包む形で、細部は作っていない」「動く仕組みは作っていない」「実機では未確認」。溝や穴の横の位置の記入が無く、図が左右同じに描かれている物は、印を付けて幅の中央に置く。道具が寸法を作ってよいのは、独立な 2 つ以上の読みが一致した記入から形が 1 つに閉じる時だけ（読み手は足し引きしない）。
- **呼び方は一般の語と寸法**（製造元の型番・製品名を使わない）。JIS・ISO の番号は出してよい。
- **保存の形の版は、新しい物を使ったファイルだけ上げる**（使っていないファイルは古い版でも開ける。例: 穴つきの面、フレームの接続の記録）。古いファイルは読めるままにする（書く時は新しい形）。
- **足す・削るの決め方は「提案して見せる」**（確定の前に予告を見せ、利用者が変えられる）。
- **用語は CAD の一般の語**（アセンブリ・ソリッド・外観）。数値の表示は有効 6 桁（全桁は説明に。許容差より小さい端数は 0。計算の中の値は変えない）。
- **既定の視点は、前・上・右が見える等角**（定数は 1 か所。画面検査を緩めずに直す）。
- **ほかの CAD は、手順の考え方だけを参考にする**（名前・画面・アイコン・データを写さない）。
- **外へデータを送る機能は作らない**（見積もり連携は不採用。部品表と切断の一覧の CSV を使う）。
- **族や設定の項目をまとめて足す**: 種類の一覧・数を数える単体・画面検査の種類の一覧を何度も変えないよう、揃った行をまとめて 1 回で入れる（カタログの担当の `wip/bundle11` の考え方）。
- **長い関数は分割する**（基準の表 `eslint.functionSizeBaseline.js`。基準は実測へ下げるだけで、上げない）。分割は動きを変えず、単独の回で送る。

### 9.4 禁止事項（rules/02 の全項目と、関連の決まり）

1. 担当は、ブラウザの窓・Electron・開発サーバー（vite dev など）を起動しない。ヘッドレスの検査（Vitest、Playwright の headless）は可。アプリの起動と終了は統括だけ。
2. Electron・開発サーバーを二重に起動しない（起動の前に、処理と待受の口を確かめる）。
3. `package.json` の依存、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、vendor のバイナリ（OCCT の WASM など）を無断で変えない。要る時は作業を止め、理由と差分の案を統括へ。
4. ビルドや検査の実行中の処理を強制終了しない（例外: 結果が出た後に 10 分以上出力が無く止まっている Playwright とその子、Codex が残した未開始の待機中の画面検査は、統括が終了してよい。毎回、報告記録に書く）。失敗した全体検査は、聞かずに止めて直してやり直す。
5. 検査の期待値を書き換えて赤を消さない。正確さ・保存の中身・入力の大きさを減らして成功にしない。性能の上限は `docs/requirements.md` §5.2 が正。
6. 警告・型エラーを封じない: `eslint-disable`、`@ts-ignore`、`@ts-expect-error`、`any`、`as unknown as`、tsconfig の strict の緩和、`.skip`・`.only`。原因を直す。
7. 統括は pnpm・npm・npx・yarn を直接実行しない。
8. 担当は git へ書かない（stash・checkout・reset を含む）。前後の比べは `git diff`・`git status` の読みだけ。
9. 担当は子エージェント（Agent・Task・Workflow・ほかの AI の道具）を起こさない。報告には必ず「子エージェントの使用: なし」「git への書き込み: なし」の 2 行。

### 9.5 品質の決まり（rules/03 の要点と、今の運用）

- git の操作は統括だけ。commit の文は日本語で、何を変え、何ができるようになったかを、専門の語を避けて具体的に。`feat:`・`fix:` などの接頭辞は使わない。本文の末尾に `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`。
- 変えたパッケージの検査だけで合格にしない（上流の変更は下流を壊す）。→ 今の運用では、送る前の単体の全件（全パッケージ）と、枝の外部検査の全部がこれを担う（§2.2・§4）。
- 検査が追跡中のファイルを書き換えたら失敗（実行の順で結果が変わるのを防ぐ）。
- 単体は 1 パッケージずつ、依存の逆順で。実形状の計算を含む model・kernel・expression は 1 worker で、性能の検査を長い機能の検査より前に回す（長い WASM の計算の直後にミリ秒の性能を測らないため）。**担当が重い組を同時に流すと、性能の検査が落ち、空きメモリーも尽きる。**
- 性能の検査（NFR-PF-2・3）は単体に含む。時間の判定は全部のモードで同じ正本（`expectWithinBudget` → `releasePerformance.ts` の `reportDuration`）。目標の小さな超過で実装を止めないが、実用の上限の超過・非有限値・停止は失敗。

- 手元の検査の道具は `scratchpad/claude/tools/diag.py`（型・lint・単体・画面検査。画面検査は機械全体で同時 1 本）。担当は根で `scripts/check.ps1` を流さない。手元の検査は、ネイティブの node（`C:\Program Files\nodejs`、arm64）と rg で流す（x64 の私有の道具では計算の期限に届かない）。

### 9.6 委譲と指示書（rules/01 §2〜§4）

- 指示書の置き場は `scratchpad/claude/instructions/<担当名>.md`。全担当の共通の規律は `scratchpad/claude/instructions/common.md`。先頭に、①子エージェントを起こさない ②git へ書かない ③触ってよいファイルの限定、をこの順で。
- 指示書に必ず入れる 7 つ: (1) 対象の実パスと関数名（統括が Grep で実在を確かめた物だけ。新規は「新規」と書く）(2) 数値の合格条件 (3) 変えてはいけない・起動してはいけない・緩めてはいけない物 (4) 段階と中間の報告（値を変えさせる前に今の値を報告させる）(5) 関係する過去の失敗（rules/06 の番号。無ければ「該当なし」）(6) 使える道具のコマンド・対象・確かめ方 (7) 成果物の保存先。
- 大きな目標を 1 回で頼まない。担当が「前提が違う」と編集の前に止まるのは、正しい対応。
- 担当は `scratchpad/claude/agents/<担当名>/progress.md` に 15 分以内ごとに追記する。統括は 20 分ごとに、更新の時刻と最後の行を直接見る。40 分以上更新が無ければ停滞として、原因の確かめ・指示の縮小・出し直し。
- 担当の台帳 `scratchpad/claude/agents/registry.md` は手で書かず、`registry.py add|set-status|archive|list` を使う。
- 担当を検査の待ちで止めない。1 件の実装と当たる単体が済んだら、すぐ次の実装に入らせる。作業ツリーへ入れる順番（写しの前後）は統括が知らせる。写しの知らせまでは、担当は wip（自分のフォルダーの下）で進め、作業ツリーを変えない。
- 製品の包みを、常に 1 本以上（できれば Opus 3 本）動かす。道具の修理は進捗に数えない。動かせる行が無ければ、利用者の判断待ちを選択肢で聞く。

### 9.7 公開（rules/05 の要点。最後の版で 1 回）

- 順番: 機能の凍結 → ヘルプと画像の更新 → 撮影 → 取扱説明書の生成 → 整合の検査（`scripts/check-release-ready.ps1`）→ 全体検査 → 公開の解説（日本語）→ 通常の CI と配布の CI → 配布物の生成と起動の確かめ → 合格の後にタグ。
- 公開の条件（最後の版）: 独立評価 2 本の低い方が 90 点以上（観点: コード品質・アーキテクチャ・可読性・性能・セキュリティ・説明書とヘルプが実際の操作に合う事・使えない機能やバグが無い事・直感的な UI/UX）、公開前検査の合格（説明書の画像が今の版の撮影、W21・W22 の証拠、起動の速さ 2 回目 ≤ 1 回目 × 0.8）、同じ版の両 OS の外部検査、導入の確かめ（無人の導入と自動の操作）。v1.0.3 限りの許容（90 点未満、起動の比）は持ち越さない。
- 配布物が揃った版では、その日のうちに公開前検査を流す。
- 解説に載せるのは、利用者の操作と画面の表示だけ（内部の計算の方式・データ構造・B-rep・Worker などの語を出さない）。
- Web 版は公開の対象外のまま。デスクトップ版が最優先。版の番号は、根と apps/desktop・apps/web の package.json、electron-builder の設定、タグで一致させる。
