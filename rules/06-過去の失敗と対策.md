# 10. 過去の失敗と対策

## 記録の義務

- 不具合、手戻り、規約違反、検査のすり抜けが起きたら、**同日中に**本書へ追記する。
- 対策は可能な限り**仕組み**(フック・検査スクリプト・CI)へ落とし込み、`rules/00-施行の仕組み.md` の表へ反映する。「気をつける」だけの対策を認めない。
- 指示書(`rules/01-役割と委譲.md` §3)には、関係する本書の項目を必ず引用する。

## 記録の様式

各項目は次の4点を必ず含める。

```markdown
## 10.N 見出し(YYYY-MM-DD)

- **起きたこと**: 観測された事実。実測値・エラーメッセージ・ファイルパスを実名で書く。
- **原因**: 確かめた原因。推測は「推測」と明記し、断定しない。
- **仕組みでの対策**: 追加・変更したフック/スクリプト/検査の実名と、何を防ぐか。
- **確認方法**: 対策が働いていることを確かめるコマンドまたは手順。
```

## 記録

## 10.1 規約フックが作業担当(サブエージェント)の pnpm 実行まで拒否した(2026-09-02)

- **起きたこと**: `.claude/hooks/block-direct-package-managers.ps1` が、統括だけでなく Agent ツールで起動した作業担当(サブエージェント)の PowerShell / Bash ツールからの `pnpm --version` も拒否した(2026-09-02 実測。拒否メッセージ「規約(rules/01-役割と委譲.md §1、rules/02-禁止事項.md)により、統括は pnpm / npm / npx / yarn を直接実行できません」)。P0 の足場作り(`pnpm install`)を作業担当が実行できない状態だった。
- **原因**: 前作 ORIGAMI3 では作業担当が Codex(別プロセス)で Claude Code のフックが及ばなかったが、本プロジェクトは作業担当も同一セッション内の Claude サブエージェントであり、`.claude/settings.json` のフックが作業担当のツール呼出にも適用される。フック設計時にこの差を考慮していなかった(実測で確認済み)。
- **仕組みでの対策**: フックに「入力 JSON の `agent_id`(サブエージェント発の呼出にだけ付く識別子)が存在し空でなければ通す」判定を追加した。無い・空文字・null・空白だけの場合は従来どおり拒否する(統括への拒否は弱めない)。自己試験 `block-direct-package-managers.test.ps1` へ6件追加(非空→通す×2、無し/空文字/null/空白→拒否×4)。`rules/00-施行の仕組み.md` の施行表へ判別方法を追記した。
- **確認方法**: `powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .claude/hooks/block-direct-package-managers.test.ps1` が32件全て合格すること。作業担当から `pnpm --version` がバージョン(実測 11.2.2)を返し、統括からは従来どおり拒否されること。

## 10.2 並列作業中の pre-commit が他担当の書きかけで落ちた(2026-09-03)

- **起きたこと**: 複数の作業担当が同時に作業ツリーを編集している状態で統括が `scripts/check.ps1 -Level Commit`(pre-commit)を実行すると、検査前後の `git status --porcelain --untracked-files=no` の比較が、コミット対象ではない別担当の未追跡・未 stage なファイルの変化まで拾ってしまい、無関係な理由で失敗した(2026-09-03 19:10〜20:05 の間に3回発生。`docs/報告記録.md` の該当項に記録)。
- **原因**: #0 の前後比較が「作業ツリー全体」を対象にしており、比較の本来の目的(「検査がコミット対象のファイルを書き換えていない」ことの保証)に対して比較範囲が広すぎた。並列運用(複数の作業担当が同時に別タスクを編集)を前提にしていなかった。
- **仕組みでの対策**: `scripts/lib/gitTreeGuard.ps1` を新設し、`scripts/check.ps1` の #0 の比較を `-Level` で分岐させた。`-Level Commit`(pre-commit)は `git diff --cached --name-only` で得た **stage 済みファイルだけ**を、ファイルごとの内容ハッシュ(`git hash-object`、失敗時は `Get-FileHash` へ後退)で前後比較する。`-Level Push`(pre-push / CI)は従来どおり作業ツリー全体を比較する(push は並列編集が無い前提のため据え置き)。stage 済みファイルが0件のときは比較を省略し警告を出す。自己試験は `scripts/check.selftest.ps1`(一時ディレクトリに専用の git リポジトリを作って検証し、終了後に削除する)。
- **確認方法**: `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check.selftest.ps1` が全件合格すること。並列作業中に統括が `scripts/check.ps1 -Level Commit` を実行しても、他担当の未 stage な変化では失敗しないこと(自担当分だけを stage してコミットする運用と組み合わせて確認)。

## 10.3 並列の検査中に性能検査が CPU 競合で落ちた(2026-09-04)

- **起きたこと**: 作業担当が並列にテストや E2E を走らせている間に統括が `pnpm run test`(性能検査 `packages/kernel/src/worker/solidPerformance.test.ts` を含む)を実行すると、CPU 競合で NFR-PF-2 / NFR-PF-3 の上限判定が落ちた。実測(2026-09-04): 重いブーリアン連鎖 99 段が 5576ms(上限 5000ms、静かなときは 3040ms)、穴 20 個が 749ms(上限 500ms、静かなときは 491ms)、100 フィーチャー初回全再計算が 12.6 秒(上限 5000ms、静かなときは 1366ms)。
- **原因**: 性能検査の上限判定は実行環境の CPU 負荷をそのまま反映するが、「タスクごとに都度コミット」(`rules/03-品質ゲート.md` §6)の運用は並列作業中にコミット前検査が走ることを前提にしており、上限判定側は静かな専有環境しか想定していなかった。
- **仕組みでの対策**: 環境変数 `POINTERCAD_PERF_STRICT` を導入した。`solidPerformance.test.ts` の各性能検査は補助関数 `expectWithinBudget(actualMs, limitMs, label)` を呼ぶよう統一し、この変数が `'1'` のときだけ `expect(...).toBeLessThan(...)` で厳密に判定してテストを落とし、それ以外は実測値の記録にとどめて失敗にしない(超過時は「[参考] 上限超過」とログに出す)。`scripts/check.ps1` は `-Level Push`(pre-push・CI・既定)のときだけ `$env:POINTERCAD_PERF_STRICT = '1'` を設定し、`-Level Commit`(pre-commit)では明示的に空にする。上限の数値と検査内容は変えない。
- **確認方法**: `pnpm --filter @pointercad/kernel run test`(環境変数未設定)が全件合格し実測値がログに出ること。`$env:POINTERCAD_PERF_STRICT='1'; pnpm --filter @pointercad/kernel run test` が厳密モードで従来どおり判定すること。`scripts/check.ps1 -Level Push` の出力冒頭に「性能検査: 厳密」、`-Level Commit` は「性能検査: 参考」と出ること。

## 10.4 作業担当が `git stash` を実行し、並行作業中の他担当の書きかけを一時的に消した(2026-09-05)

- **起きたこと**: 作業担当(P5 タスク17)が自分の検査のために `git stash` を実行し、そのとき並行して動いていた他の作業担当(P5 タスク11 ほか)の書きかけ 8 ファイルが数分間 HEAD の状態へ戻った。`stash pop` が `statusText.ts` の競合で止まり、担当は 7 ファイルを `git show stash@{0}:<path>` から `cp` で復元して切り抜けた。統括が事後に `git stash` の中身と作業ツリーを比較し(作業ツリーが上位集合であること: `statusText.ts` +25 行、`createSolidLayer.test.ts` +2 行、他は一致)、実害(編集の消失)が無いことを確認してから `git stash drop` した(`docs/報告記録.md` 2026-09-05 11:08 の追記)。同じ担当が検査のために Agent ツールで別の担当を起こす違反も同時に自己申告した(結果は使わず前景で再実行、実害なし)。
- **原因**: 指示書・`rules/01-役割と委譲.md` §1 は「作業担当はgitへ書き込まない」と定め、本文中に commit / push / checkout / merge / stash / reset を禁止対象として列挙しているが、`stash` は一時退避で「書き込み」という自覚が薄く、担当が検査の前後比較を自己流(`git stash` で作業ツリーを一時的に空にして検査し直す発想)で行おうとした(推測)。複数の作業担当が同一の作業ツリーを共有する構成(`rules/01-役割と委譲.md` §1 冒頭)では、`stash` は自分の変更だけでなく他担当の未コミットの変更も一緒に退避してしまい、`pop` の競合で復元が遅れる間、他担当からは自分の書きかけが消えたように見える。
- **仕組みでの対策**: 指示書に明記する禁止事項の定型へ「git への書き込み禁止(`git stash` を含む)」を1文として加える(`rules/01-役割と委譲.md` §2 に追記、次のコミットで反映)。検査の前後比較は `git diff` / `git status` の**読み取りだけ**で行い、作業ツリーを退避・復元する操作(`stash` に限らず `checkout` / `reset` 等の書き込みを伴うもの)を作業担当に一切させない。
- **確認方法**: 新しく書く指示書の禁止事項の並びに「`git stash` を含む」の一文があること(`rules/01-役割と委譲.md` §2 を目視)。作業担当に委譲したタスク完了後、統括が `git status` で git 未書込を確認する際、stash の記録(`git stash list`)が空のままであること。
- **追記(2026-09-06)**: 作業担当(ロフトの修正)が「直す前に赤くなることを確かめる」ために `git stash push -- <1 ファイル>` / `pop` を約4分使った(`stash list` は空、欠落なし——統括が確認)。上記の禁止の理由をここに再掲する: **「直しを一時的に外して赤を確かめる」は通常の編集(該当行を元に戻して保存 → 検査 → 直しを再適用)で行う**。指示書の冒頭の定型文に「`git stash` / `checkout` / `reset` は使わない(rules/06 10.4)」を入れる(統括の運用)。

## 10.5 作業担当の書きかけが残る作業ツリーで Electron 台本を組み、真っ暗な窓のまま起動した(2026-09-05)

- **起きたこと**: 統括がまとめコミット後の作業ツリーで Electron の確認台本を組み直したところ、その時点で並行の作業担当(P5 タスク11・16・17・28)がすでに次の書きかけを作業ツリーへ加えており、renderer のビルドにその書きかけが混ざった。起動した Electron の画面が最初の項目(`boundingBox` の取得)から全部 30 秒待ちで落ち、画面が真っ暗なまま残った。利用者が黒い窓に気づいて質問し、統括が台本を止めて electron の残プロセス 3 つを終了した(`docs/報告記録.md` 2026-09-05 10:55 の追記)。
- **原因**: Electron の台本は `apps/desktop` の renderer を作業ツリーから都度ビルドして起動するため、**ビルドした瞬間の作業ツリーの状態をそのまま画面に映す**。全体検査(`scripts/check.ps1`)は並列作業中の書きかけに影響されないよう「静かな切れ目」まで待つ運用が既にあった(`rules/06` 10.2・10.3)が、Electron 台本の実行にはその運用を適用していなかった。
- **仕組みでの対策**: **Electron の台本は、作業担当が書きかけを持つ間は組まない。** 全体検査(`scripts/check.ps1`)を実行する「静かな切れ目」(委譲中の作業担当がいない、待ち行列が空、`git status` が報告記録以外で汚れていない)とまったく同じ条件がそろってから、統括がビルド・起動・確認・終了までを行う。機械施行は無く、統括の手順として本書へ記録し、委譲の再開判断(`rules/01-役割と委譲.md` §4 の停滞監視と同様に統括が都度確認する項目)に含める。
- **確認方法**: Electron 台本を起動する前に、統括が「新規の委譲が進行中でないこと」「待ち行列(`queue/*.job`)が空であること」「`git status --porcelain` が報告記録の追記以外で汚れていないこと」の3点を確認し、その結果を `docs/報告記録.md` の同じ追記に書き添えること。

## 10.6 作業担当が指示書の禁止に反し、Agent ツールで別の担当を起こした(2026-09-05、3件)

- **起きたこと**: 指示書は「Agent ツールで別の担当を起こさない」と定めていたにもかかわらず、作業担当が3件、自分の作業中に Agent ツールを使って別の担当を起こした。①P5 タスク17の担当: 検査のために Agent ツールへ委譲(結果は使わず前景で再実行、自己申告。`docs/報告記録.md` 2026-09-05 11:08)。②P4b 仕上げ22aの担当: 検査を一度 Agent ツールへ委譲(結果は使わず前景で再実行、自己申告。同 01:10 の追記)。③P5 タスク29の担当: 検査を丸ごと Agent ツールへ委譲。3件とも結果はどれも使わず本人が前景で検査をやり直したため実害は無かったが、トークンの二重消費と、統括の把握していない範囲で別の担当が動く(何をしたか統括が検査していない)状態が生じた。
- **原因**: 指示書には「Agent ツールで別の担当を起こさない」という禁止が末尾近くの1文として埋もれており、担当が「検査くらいは委譲してよい」「丸ごと任せれば早い」と読み違えた(推測)。禁止の理由(統括の把握外で作業が進む、実装者が自分自身を検査する構図に戻ってしまう ── `rules/01-役割と委譲.md` §1の理由と同じ)を明文化していなかった。
- **仕組みでの対策**: `rules/01-役割と委譲.md` §2の指示書の定型を並び替え、**「Agent ツールで別の担当を起こさない(検査も自分で前景で実行する)」を規律の最初の行**に置く(埋もれさせない)。あわせて、**担当からの報告には必ず「Agent ツールの使用: なし」(使った場合は何にどう使ったかを明記)の1行を含めさせる**規約を追加した。この1行が報告に無ければ、統括は報告を差し戻して書き直させる(自己申告に頼るのではなく、明記を毎回強制する)。
- **確認方法**: 新しく書く指示書の1行目(規律の最初の行)が「Agent ツールで別の担当を起こさない(検査も自分で前景で実行する)」であること(`rules/01-役割と委譲.md` §2を目視)。作業担当からの報告に「Agent ツールの使用: なし」(または使用内容)の1行があることを、統括が受け取るたびに確認する。

## 10.7 コミット前検査が「作業ツリー全体」を対象にしていたため、並列作業中の待ち行列が詰まった(2026-09-05)

- **起きたこと**: pre-commit の `scripts/check.ps1 -Level Commit` は stage 済みファイルの前後比較(#0)こそ限定していたが、typecheck / lint / test / build 自体は依然として**作業ツリー全体**に対して実行していた。5〜6件の作業担当が並行して書きかけを持つ状況では、作業ツリーの typecheck が「その瞬間に全部緑」になることがほぼ無く、報告記録だけのコミット(待ち行列の job 300)が 12:11 から 90 分・15 回以上再試行しても載らなかった(`docs/報告記録.md` 2026-09-05 13:41 の追記)。
- **原因**: 10.2 の対策(#0 の前後比較を stage 済みファイルだけに限定)は「検査がコミット対象を書き換えていないか」の確認範囲だけを絞ったもので、**検査そのものの実行対象(typecheck/lint/test/build が読むソースの範囲)は作業ツリー全体のままだった**。並列運用(複数の作業担当が同時に別タスクを編集)を前提にしていなかった点は 10.2 と同根。
- **仕組みでの対策**: `scripts/check.ps1 -Level Commit` を「stage 済みの差分だけを写した別の作業ツリー」で検査するよう改めた。`scripts/lib/gitTreeGuard.ps1` に次の関数を追加(単一正本、`check.ps1` と `check.selftest.ps1` の両方が dot-source する)。
  - `New-StagedTreeWorktree`: `git worktree add --detach --quiet <一時ディレクトリ> HEAD` で HEAD の写しを作り、`git diff --cached --binary --output=<file>` で書き出した stage 済みの差分を `git apply --binary --whitespace=nowarn` で写しへ載せる(新規・削除・改名を含む)。適用できなければ理由(終了コード)を添えて `Ok=$false` を返す。
  - `New-NodeModulesJunctions` / `New-RootNodeModulesShadow`: 写しの中へ `node_modules`(根、`packages/*`、`apps/*`、`e2e` のうち実体があるもの)を**コピーせずジャンクション**で元へ向ける。**根の `node_modules` だけは実体ディレクトリを作り直下の項目を個別にジャンクション/コピーする**(2026-09-05 実測: pnpm 11.25.0 の recursive 実行は実行状態の記録先(`.pnpm-task-run-state-v1`)を根の `node_modules` 直下に置き、根自体がジャンクションだと `ERR_PNPM_UNSAFE_TASK_RUN_STATE_PATH` で `pnpm run test` / `run build` を拒否した。`packages/*`・`apps/*` にはこの制約が無い)。
  - `Remove-JunctionSafely` / `Remove-StagedTreeWorktree`: **ジャンクションを個別に(`[System.IO.Directory]::Delete($path, $false)` で非再帰に)外してから** `git worktree remove --force` で写しを片付ける。**この順序を逆にすると危険**: 2026-09-05 の再現実験で、写し直下に `node_modules` ジャンクションを残したまま `git worktree remove --force` を実行したところ、ジャンクションを辿って**実体側(ジャンクション先)の内容が削除された**(`git.exe` が内部でどう辿っているかは未確認だが、実害としてリンク先のファイルが消えることを確認)。一方、Windows PowerShell 5.1 の `Remove-Item -Recurse -Force`(ジャンクションを直接指定、または親ディレクトリごと)はジャンクション先を辿らず安全だった(同日実測、使い分けは同ファイルのコメント参照)。
  - `-Level Push` は変更していない(作業ツリー全体、前後比較あり。並列編集が無い前提のまま)。
  - 写しの中で検査するため、Commit の前後比較(#0)自体を不要として省いた(`rules/03-品質ゲート.md` §7.1 に反映)。
  - 自己試験を `scripts/check.selftest.ps1` に追加: (a) stage 済みの差分だけが写しに載り、作業ツリーの未 stage な壊れたファイルは写しに現れない、(b) 片付け後に `git worktree list` へ残らずジャンクション先の実体(precious.txt)が無事、(c) 適用できない patch は理由を出して `Ok=$false` になり、かつ後片付け漏れが無い。
  - **実測(2026-09-05)**: 機構自体の上乗せは僅少(`New-StagedTreeWorktree` 約1.6秒 + `New-NodeModulesJunctions` 約0.15秒 + `Remove-StagedTreeWorktree` 約0.3秒 ≒ 合計2秒程度)。実際に `check.ps1 -Level Commit` を実行した際の総所要は約39秒(typecheck の実エラー4件で1段目のみ実行、以降は未実行)。tsc の増分ビルド(`tsconfig.tsbuildinfo`)キャッシュを写しへコピーする案も試したが、並列開発中はキャッシュがほぼ無効になり**かえって遅くなった**(typecheck 単体: コピー無し 18.0 秒 / コピーあり 27.5 秒)ため不採用。

## 10.8 実際の pre-commit の中で `git worktree add` が毎回失敗した(GIT_INDEX_FILE の継承、2026-09-05)

- **起きたこと**: 10.7 の対策(写しによる検査)を実装した直後、統括が実際の `git commit`(pre-commit フック経由)で `scripts/check.ps1 -Level Commit` を走らせたところ、`New-StagedTreeWorktree` の `git worktree add` が毎回 `fatal: Unable to create 'C:/.../pointercad-commitcheck-<guid>/.git/index.lock': No such file or directory`(終了コード128)で失敗した。`scripts/check.selftest.ps1`(フックの外で実行)はこの問題を検出できていなかった。

- **仕組みでの対策**: `scripts/lib/gitTreeGuard.ps1` に `Clear-InheritedGitEnv`(`GIT_DIR` / `GIT_INDEX_FILE` / `GIT_WORK_TREE` / `GIT_PREFIX` / `GIT_COMMON_DIR` / `GIT_OBJECT_DIRECTORY` / `GIT_ALTERNATE_OBJECT_DIRECTORIES` / `GIT_QUARANTINE_PATH` を退避して削除し、退避内容を返す)と `Restore-InheritedGitEnv`(退避内容を戻す)を追加した。`New-StagedTreeWorktree` と `Remove-StagedTreeWorktree` は本体全体をこの退避/削除〜復元で包み、`scripts/check.ps1` の `-Level Commit` 分岐でも写しの中で `pnpm run typecheck/lint/test/build` を実行する間だけ同様に消す(いずれも `try/finally` で必ず元に戻す)。
- **確認方法**: `scripts/check.selftest.ps1` にシナリオ10(`$env:GIT_DIR=".git"`・`$env:GIT_INDEX_FILE=".git/index"` を設定した状態で `New-StagedTreeWorktree` → `Remove-StagedTreeWorktree` を呼び、写しが作れて stage 済み差分が正しく適用され、片付けも `git worktree list` に残らないこと)を追加し、全件合格すること。**実際の pre-commit(統括の `git commit`)で `scripts/check.ps1 -Level Commit` が `git worktree add` の失敗なく最後まで進むこと**を統括が確認する。

## 10.13 OCCT(embind)のオブジェクトの持ち主を見分けられず二重解放・解放漏れを起こした(2026-09-06)

- **起きたこと**: P6 タスク7・8(kernel の XCAF・STEP 書き出し/読み込み)で、OCCT(embind)の戻り値の「持ち主(誰が delete すべきか)」を見分けられず、3 件の解放事故が起きた。①`XCAFDoc_DocumentTool.ShapeTool(...).get()` の戻り(**借り物**)を delete し、以後の解放が `memory access out of bounds` で落ちた。②`TDocStd_Document` を `Handle_TDocStd_Document_2` に包んだ後も**文書そのもの**を解放の控え(allocations)に積んでおり、二重解放で WASM が壊れた。③`STEPCAFControl_Reader.Reader()` / `ChangeReader()` の戻り(**`const T&` を embind が複製で返す**)を解放しないまま使い続け、504 面の STEP 読み込みが 9,081ms かかった(解放するよう直した後は 2,859ms、**3 倍の差**)。
- **原因**: embind は C++ の戻り値の意味(借り物の参照か、複製されたオブジェクトか、Handle に持ち主が移ったか)を型定義だけからは示さず、**呼び出しごとに実行時の挙動を確かめないと判別できない**(P5 §1.4 の教訓「型定義に載っていても実行時にあるとは限らない」と同根で、今回は「実在するか」ではなく「誰が解放するか」が未確認だった)。`Handle_X.get()` が借り物を返すこと、`new` した本体を `Handle_X_2(本体)` に包むと持ち主が Handle 側へ移ること、`const T&` を返す API の戻りが複製であることのいずれも、事前の型定義からは読み取れず実測が要る。
- **仕組みでの対策**: **見分け方を次の 3 点に固定する。** ①`Handle_X.get()` の戻りは**借り物なので delete 禁止**。②`new` した本体を `Handle_X_2(本体)` に包んだら**持ち主は Handle に移る**(本体そのものは解放の控えに積まない)。③**`const T&` を返す API の戻りは複製**であり、使い終わったら delete が要る(忘れると解放されないオブジェクトが溜まり、③の実測のとおり数倍遅くなる)。**迷ったら「確保と解放の回数を数える口」で検査に固定する**(P5 §4 で導入した `createAllocations()` の注入と、タスク7 の検証表にある「確保したものの解放: `delete()` の回数が確保の回数と一致」の検査パターンを、新しい OCCT の API を使うたびに横展開する)。`rules/01-役割と委譲.md` の指示書の「読むもの」に本項を追加し、**kernel の `occt/` に新しい OCCT の API を使うときは実測で持ち主を確かめて注釈に書く**ことを手順とする。
- **確認方法**: kernel の `occt/xcafDocument.ts` / `readStep.ts` の該当検査(「確保したものの解放」)が緑であること。新しい OCCT の API を追加する変更のレビュー時に、その API の戻り値の持ち主(借り物 / 複製 / Handle 移管)が注釈に書かれていることを確認する。STEP 読み込みの性能検査で、解放漏れによる数倍の劣化が再発していないこと(504 面の読み込みが目安値(実測 2,859ms 程度)から大きく外れていないこと)。

## 10.14 CPU 絞りで長い計算を作る E2E が共有ランナーで時間切れになった(2026-09-06)

- **起きたこと**: GitHub Actions(`f708ab6`、run 33998506476)の windows-latest で、`solid.spec.ts` の「長い計算のあいだだけ進み具合と『中止』が出る」(NFR-PF-4)だけが `Test timeout of 180000ms exceeded` で失敗した(ubuntu-latest は 5 段すべて成功、windows も残り 66 件は緑)。後始末の `setCPUThrottlingRate(1)` が出す「Target page, context or browser has been closed」は結果であって原因ではない。
- **原因**: CDP の CPU 絞り(1/20)は「その機械の速さの 1/20」であって絶対の長さではない。2 コアの共有ランナーでは、手元の機械なら間に合う 23 段の計算が 3 分(180 秒)に収まらなかった。`rules/06` 10.3・10.12 と同根——**検査の所要が実行機の速さに比例する作りだった。** 上限(タイムアウト)を延ばすのは解にならない(実行機がさらに遅ければ同じことが起きる)。
- **仕組みでの対策**: 検査専用の口 `window.pcadDebugStepDelayMs` を `packages/model/src/kernelBridge.ts` の `toCancelProxy` に 1 つ足した(正の数のときだけ、段と段の間の中止の問い合わせを遅らせる。Comlink は戻りの Promise を待つので Worker 側の計算そのものが延びる。**通常の道は Promise すら作らないので、本番の挙動には影響しない**)。`solid.spec.ts` の当該 E2E は CPU 絞りを廃し、**8 段 × 200ms の固定の計算**を作って、帯・`aria-valuemax`・文言・中止・「中止後に段が進んでいない」を従来どおり確かめる(期待値はすべて定数から導く。緩めていない)。**E2E で長い計算を作るときに `Emulation.setCPUThrottlingRate` を使わない。**

## 10.15 長い検査(push 前検査)をセッションから切り離す(2026-09-06)

## 10.18 E2E の並列本数を機械任せにして、初回のカーネル読み込みが検査の上限を越えた(2026-09-06)

- **起きたこと**: push #14 の E2E で `p5-cut-mirror`「切断で体積が半分」・`p5-primitive-pick`「箱を置いた直後に選べる」・`p4b-timeline`「独立した2つの押し出し」の3本が、体積「計算できていません」のまま60秒で赤になった(静かな窓での再実行でも再現)。原因は `e2e/playwright.config.ts` に `workers` の指定が無く、Playwright の既定「論理コア数 ÷ 2」がこの機械(12コア)で6並列になっていたこと。検査は1本ごとに新しいブラウザ文脈を作り、文脈ごとに50MBのOCCT WASMをもう一度コンパイルするため、6並列では初回のカーネル読み込みが1並列の17〜30秒から55〜80秒に延び、spec の `KERNEL_TIMEOUT_MS` 60秒を越えた。落ちた4〜8秒後には必ず `isComputing` が false(詰まりではなく上限不足)で、Worker は生存し pageerror / console.error は0件だった。7回の再現実験(6並列: 1/3/0/6/0/6本赤、1並列: 全緑17〜30秒)で確かめた。push #12 が緑・#14 が赤だったのは境界の揺れであり、疑った (a) `documentVersion` の購読・`toCancelProxy`・viewport/store の変更、(b) localStorage はいずれも白だった。

- **確認方法**: `e2e/playwright.config.ts` の `workers` が `2` に固定されていること(値を目視)。当該3 spec が `pcadRecomputeStats().isComputing` の下りを待ってから体積を確認していること。`pnpm run test:e2e` を実行した機械のコア数に関わらず、実際に使われる並列数が2であること(Playwright の実行ログの worker 数を確認)。

## 10.35 未収束の合致を証明済み矛盾としてE2Eに期待した(2026-09-09)

- **起きたこと**: 一致0mmと距離10mmを同じ2部品へ付けるE2Eで、`provenConflictMateIds`に2本目が入ると期待したが空だった。木には両方へ「両立を確認できません」と正しく出た一方、プロパティは疑いを読まず「解決済み」と誤表示した。
- **原因**: 可動部品を含む2条件は最小二乗の未収束から両立不能が疑われても、固定同士の定数残差のような数学的証明にはならない。計画書の「原因の合致が指される」を「証明済みの矛盾」に強めて解釈し、プロパティの状態分岐も証明済みだけを見ていた。
- **仕組みでの対策**: `assemblyMatePropertyState`へ未解決・証明済み・両立未確認・解決済みの順を集約し、木と同じ診断区分を表示する。純関数検査が4状態と優先順位を固定する。E2Eは`provenConflictMateIds`を空のまま、`suspectedConflictMateIds`の原因IDと木・プロパティの「両立を確認できません」を確認する。
- **確認方法**: UI単体検査とP7 E2E (c)が緑になり、証明のない条件を「矛盾」と表示しないこと。

## 10.36 実装コミットを別のHEADへ置き、完了タスクを1件だけ計上した(2026-09-09)

- **起きたこと**: 利用者が「実装は10件以上まとめ、都度mainへ着地」と指示した後も、検査用のdetached HEADと実際のmainを区別できない報告を行い、さらに複数の変更を含むコミットで完成度を1件しか増やさなかった。利用者がpush可能なコミットを確認できず、同じ指示を繰り返すことになった。
- **原因**: コミット直前のブランチ確認と、`HEAD`からstage済み進捗台帳までに新しく完了したタスクID数の確認が手順だけだった。検査用worktreeのコミット可能性と本体mainへの着地を機械的に区別せず、変更ファイル数を完了タスク数へ対応付ける正本もコミット条件へ接続していなかった。
- **仕組みでの対策**: `scripts/check-commit-batch.ps1`をpre-commitの最初に実行する。実装ファイルがstageされている場合は、(1)現在ブランチが`main`、(2)`docs/progress.json`がstage済み、(3)`HEAD`では未完了だったIDが10件以上追加、(4)`reportedCompleted`の増分が追加ID数と一致、(5)既存完了IDの削除が0件、を満たさなければcommitを止める。文書だけのcommitも`main`を必須とする。判定本体を`lib/commitBatchGuard.ps1`へ分け、自己試験が文書のみ・9件拒否・10件許可・main以外拒否を固定する。
- **確認方法**: `scripts/check-commit-batch.selftest.ps1`が4条件すべてに合格すること。実際のコミット直前に`check-commit-batch.ps1`がブランチ`main`と新規完了ID10件以上を表示し、その後に通常の`check.ps1 -Level Commit`が始まること。完成度はコミット後の`docs/progress.json`だけから報告する。

## 10.37 50部品の操作中描画が共有CIで30fpsをわずかに下回った(2026-09-09)

- **起きたこと**: P7完了E2Eは手元で38.6 / 43.7 / 38.0fpsの3回連続合格後にmainへ着地したが、共有CIでは29.320fpsとなり、NFR-PF-1の最低30fpsを0.680fps下回った。直前の8.65fpsからは改善していたものの、品質ゲートは正しく失敗した。
- **原因**: 操作中の描画倍率0.4は縦横を40%、画素数を16%へ減らす設定だったが、共有CIのソフトウェア描画負荷の揺れに対して2.3%の不足を吸収できる余裕が無かった。またE2Eの記録がfpsだけだったため、描画回数不足と測定区間の伸びをログから分けられなかった。
- **仕組みでの対策**: 操作中の倍率を0.3へ下げ、画素数をCSS面積の9%へ固定する。中ボタンを離した直後には従来どおり端末の通常pixel ratioで1枚描くため、静止画の品質は変えない。`viewportRenderScale.test.ts`が0.3と高精細端末での実効0.6を固定し、50部品E2Eはfpsに加えて完了描画数と測定時間を必ず出力する。
- **確認方法**: `scripts/check.ps1 -Level Push -E2EOnly -E2EGrep "空状態、原点・式配置" -E2ERepeats 3`で39.4fps(86描画/2182.2ms)、37.3fps(79描画/2117.6ms)、43.5fps(93描画/2136.9ms)の3回連続合格。最終的には指定なしの`-Level Push`も省略せず通す。
