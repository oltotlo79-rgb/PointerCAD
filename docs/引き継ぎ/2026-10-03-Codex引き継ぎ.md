## 5. 道具と手順

### 5.1 配達（コミット→検査→送信）: `scratchpad/claude/tools/deliver.py`

ルートで確定した変更を、検査用の独立コピー `scratchpad/c3` へ写し、そこで検査→コミット→送信する。

1. **画面検査の証拠の照合**: `python -B -X utf8 scratchpad/claude/tools/e2e_coverage.py check --worktree`
   - 変えた e2e の spec ごとに、合格した画面検査の記録があるか（OPS-29）。
   - 足りなければ、その spec を `diag.py e2e` で流す。
   - 免除は除外の一覧に書く。例: `scratchpad/claude/deliveries/excludes-V101.txt`。書式は `<spec> e2e-waive:<project|*> <owner> <理由>`。
2. **スナップショット**: `python -B -X utf8 scratchpad/claude/tools/deliver.py snapshot [--excludes <一覧>] [--allow-revert <パス>]`
   - 配達の ID（例 `20261003-155732`）が出る。
   - 撮り直しの画像が過去の版と同じ内容に戻った時は `--allow-revert <画像のパス>` で許す（v1.0.2 で1枚あった）。
3. **同期**（必ず先に確認だけ）:
   - `deliver.py sync --delivery <ID> --dry-run` → `deliver.py sync --delivery <ID>`
   - c3 に前の残りがあると止まる。ルートが HEAD と一致することを確かめてから、c3 で `git restore --staged --worktree` / `git rm --cached` で HEAD に戻す。
4. **一括件数の例外の承認ファイル**（完了した原タスクが10件未満の時。公開の時は毎回要る）:
   - `scratchpad/c3/.git/pointercad-commit-batch-approval.json` を新しく書く。
   - 中身は `{approvedBy:"user", reason, base:<HEAD の SHA>, tree:<c3 で git write-tree の値>, recordedBy:"orchestrator", recordedAt:<今の時刻>}`。
   - 古いファイルを sed で書き換えない。新しく書く。
5. **コミットの文**: `scratchpad/claude/deliveries/<ID>/commit-message.txt`。日本語で、変えたことの要約と末尾の行。
6. **送り先のブランチを作る**（新しい公開の候補の時）:
   - `gh api repos/:owner/:repo/git/refs -f ref=refs/heads/feature/release-v<版> -f sha=<基の SHA>`
7. **検査と送信**:
   - `deliver.py gate --delivery <ID> --message <文のファイル> --push-ref refs/heads/<送り先> --scope local`
   - 背景で約75分。進捗は `deliver.py status --delivery <ID>` と `scratchpad/claude/deliveries/<ID>/gate.log`。
   - main・`feature/release-*` へ送る時は、README の配布の導線の版と `docs/releases/v<版>.md` の有無を先に確かめる。欠けていれば送らない（cx-t03 の守り）。
   - gate.log には、品質ゲート自身の自己試験がわざと出す `[NG]` が約16行ある。本物の失敗は、本番の段の `=== (1/5)`〜`(5/5)` の後の `[NG]` と、`state.json` の `exitCode`・`status` で判断する。
8. **ルートを送った版へ進める**: `deliver.py sync-root --delivery <ID> --dry-run` → `deliver.py sync-root --delivery <ID>`。次のスナップショットと公開前の確認の前に必ず行う。
9. **main への統合**（公開の後）:
   - `scratchpad/claude/state/main-release-integration.json` を `{approvedBy:"user", reason, tag, sha, recordedBy, recordedAt}` で書く。
   - `deliver.py recheck --push-ref refs/heads/main --push --dry-run` → `--dry-run` を外して実行（約75分、合格後に自動で送る）。

### 5.3 検査の実行: `scratchpad/claude/tools/diag.py`

- `unit` / `lint` / `typecheck` / `static` / `e2e` / `wait` / `status`。
- 重い検査の枠は3つ。画面検査は機械全体で1本（排他）。撮影は自動で排他になる。
- `diag.py wait` は1回の呼び出しで1回だけ使う（2回続けると Bash の10分の上限を超える）。
- 結果は `scratchpad/claude/runs/<RUN_ID>/`（`output.log`・`result.json`・`test-results/`）。
- **Codex の担当（`PCAD_WORKER_KIND=codex`）は `diag.py e2e` を拒否される。**
- 機械は Snapdragon X（ARM64）。Playwright のブラウザーは x64 の変換で動き、CPU が絞られると画面検査が2〜10倍遅くなる。
  - 180秒の打ち切りは、まず機械の速さを疑う（`Get-Counter '\Processor Information(_Total)\% Processor Performance'`）。
  - 打ち切りの印は error-context.md の「Test timeout of 180000ms exceeded」。
  - 1本ずつ（他と重ねず）流し直して、通るかを確かめる。

### 5.4 説明書の画像の撮り直し（S5）

### 5.5 公開の台本（v1.0.2 で作り、誤りを直した）

- `scratchpad/claude/tools/release_publish.ps1 -Version <版> -RunId <配布 CI の run> -OutDir <フォルダー> -Stage prepare|draft|publish [-Execute]`
