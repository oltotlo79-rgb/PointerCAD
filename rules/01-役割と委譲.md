# 2. 作業担当(Claude のサブエージェント)の起動と使い方

- 統括が Claude Code の Agent ツールで `general-purpose` の担当を背景起動する。指示書は `scratchpad/claude/instructions/<担当名>.md`(Git 無視領域)に書き、全担当に共通の規律は `scratchpad/claude/instructions/common.md` に置く。起動時の依頼文でこの2つを読ませる。指示書には、次の規律を**この順で(1行目に①)**必ず明記する。
  1. **「子エージェント(Agent / Task / Workflow ツール・他の AI ツール)を起こさない(検査も自分で実行する)」**(`rules/06-過去の失敗と対策.md` 10.6。検査の丸投げ・二重確認の代行も含めて禁止する)。
  2. **「gitへの書き込み禁止(`git stash` を含む)」**。検査の前後比較は `git diff` / `git status` の読み取りだけで行わせ、作業ツリーを退避・復元する書き込み操作(`stash` に限らず `checkout` / `reset` 等)を一切させない(10.4)。
  3. **「触ってよいファイルの限定」**。
  可能な限り複数の担当を並列で起動するが、工程・検査・品質を省かない。各指示には触ってよいファイル、触らないファイル、担当重複の無い範囲を実パスで明記する。**担当からの報告には必ず「子エージェントの使用: なし」と「git への書き込み: なし」の 2 行を含めさせる**(使った・書いた場合は何をどうしたかを明記)(10.6)。この 2 行が無い報告は、統括が差し戻して書き直させる。
- モデルは難易度で使い分ける(2026-09-23 利用者指示)。**単純な作業・機械的な置換・集計・一覧作成・文言修正・定型の検査実行 = `sonnet`(Sonnet 5)、判断が必要な複雑な作業(設計・原因究明・UI の配線・数式と形状の依存・OCCT の難所・競合の解決・全体レビュー) = `opus`(Opus 5.5)**。推論の深さは指定しなければセッションの値(利用者設定の max)を継承する。**Fable は使わない。** 2026-09-24 からは Codex の `gpt-6-astra`（最高難易度: 合致ソルバ・OCCT の難所・形状と数式の依存・競合の解決・全体レビュー。推論 `xhigh`）と `gpt-6-sol`（判断が要る実装・原因究明・UI の配線・網羅の点検。推論 `high`）も使える。Claude の利用上限は統括と Claude の担当全員で共有するため（06 §10.319）、新しい実装タスクは Codex へ多く割り当て、Claude の担当は途中の作業の完了と、Claude でないと質が落ちる作業に使う。opus の同時実行は3本までを目安にする。質を落とさずトークンを節約するため上位モデルは必要なときだけ使い、起動ごとに選んだモデルと理由を1行で記録する。

# 3. 作業担当へ渡す指示の書き方

- 粗い依頼は禁止する。指示書には必ず次の7項目を含める。
  1. 対象のファイルパスと関数名を、略称でなく実名で記す。記載前に統括が Grep 等で実在を確かめる。実在を確かめられない実名は書かない(新規作成ファイルは「新規」と明記する)。
  2. 合格条件を数値で記す(例: 「typecheckのエラーが0」「対象テストがN件全て緑」「操作の応答が500ms以内」)。
  3. 変更・起動・緩和してはいけないものを列挙する。
  4. 作業を段階に分け、各段階で中間報告を義務づける。具体値を変更させる前に現在値を報告させる。
  5. 関係する過去の失敗例(`rules/06-過去の失敗と対策.md`)と、その原因を記す。該当が無ければ「該当なし」と書く。
  6. 使用可能な道具について、コマンド、対象、確認方法まで具体的に記す。
  7. 成果物の保存先パスを明記する。
- 達成単位は小さく区切り、大目標を1回で依頼しない。担当が「前提が違う」と編集前に止めたら正しい対応として扱う。
- 理由: 大きく曖昧な依頼、存在しない実名、古い現在値は、合格の自己判断、無効な作業、失敗の再発を招くため。

# 4. 委譲後の停滞監視

- 長時間の委譲では、指示書に「進捗を `scratchpad/claude/agents/<担当名>/progress.md` へ15分以内ごとに追記する」と記し、統括は完了通知を待つだけでなく**20分間隔で**(2026-09-23 利用者指示)各担当の進捗ファイルの更新時刻と最終行を直接確認する。
- 「プロセスが生きている」「CPUを使っている」だけでは進行と判定しない。40分以上更新が無ければ停滞とみなし、原因確認、指示の縮小・修正、再委譲を行う。
- 停滞や異常は利用者が気づく前に検知して対処し、`docs/報告記録.md` へ記録する。
- 理由: 返信・プロセス・CPU・ファイル更新のどれか1つだけでは、空回りと長時間処理を区別できないため。
