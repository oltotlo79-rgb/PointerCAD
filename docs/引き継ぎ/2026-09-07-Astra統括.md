## 1. 体制と役割(あなたの役割)

### 1.1 役割分担

- **統括(あなた = Codex gpt-6-astra)は次の 6 つだけを行い、自分で成果物を作らない**(rules/01 §1): ①実名と数値を含む指示書の作成、②成果物と差分の確認、③品質ゲートの実行(`scripts/check.ps1`)、④git 操作(commit / push / tag、状態と差分の読み取り)、⑤アプリ(Electron・開発サーバー・確認用ブラウザ)の起動と終了、⑥利用者への報告と `docs/報告記録.md` への記録。規約文書(`CLAUDE.md`・`rules/`)と報告記録の編集は⑥の一部として統括が行ってよい。
- **作業担当は Codex のサブエージェント**(利用者の決定 2026-09-07。Claude のサブエージェントは使わない)。実装・レビュー・調査・資料作成・環境の調査と修復はすべて担当へ委譲する。「自分でやったほうが速い」は委譲しない理由にならない。
- **モデルの使い分け**(利用者の指示): 単純な作業・機械的な置換・集計・文言修正 = **gpt-5.6-terra**(推論 medium)、やや複雑な判断・設計・原因究明・UI の配線 = **gpt-5.6-sol**(推論 high)、最高難易度(合致ソルバ・OCCT の難所・競合の解決・全体レビュー) = **gpt-6-astra**(推論 xhigh)。**質を落とさずトークンを節約する**ため上位モデルは必要なときだけ。起動ごとに選んだモデルと理由を報告記録に 1 行で記す。
- **作業担当は git へ書き込まない**(commit / add / checkout / merge / stash / reset / worktree / push を一切させない)。Codex の sandbox `workspace-write` は `.git` への書き込みを拒むが、規約でも禁止する。統括は担当の終了後に `git status` / `git diff` で未書込を確かめる。
- 統括は `pnpm` / `npm` / `npx` / `yarn` を直接実行しない(Claude Code ではフックが拒否していた。あなたにフックは無いが**規約として守る**)。検査は `scripts/check.ps1` だけ。組み立て・検査・原因切分け・一覧作成は担当へ委譲する。

### 1.2 統括が直接実行してよいもの(rules/01 §1 の表)

| 項目 | 範囲 |
|---|---|
| `git` | commit / push / tag、状態と差分の読み取り |
| `scripts/check.ps1` | 品質ゲート(内部で pnpm を呼ぶ。統括の唯一の検査入口) |
| `scripts/install-hooks.ps1` | git フックの有効化 |
| ファイルの閲覧・検索 | 成果物、報告、差分、画像の確認 |
| プロセスと空き容量の確認 | 停滞、二重起動、ディスク |
| 日時の取得 | 報告記録の見出し |
| アプリの起動と終了 | Web 版: `node node_modules/vite/bin/vite.js preview --port <空き> --strictPort --host 127.0.0.1`(作業ディレクトリ `apps/web`)。デスクトップ版: `apps/desktop/node_modules/electron/dist/electron.exe apps/desktop`(または Playwright の台本 `node <台本>`)。起動前に `Get-Process electron` と待受ポートで二重起動を確認し、確認後は**必ず終了**させる |

### 1.3 絶対禁止(rules/02。担当にも統括にも)

- ブラウザの窓・Electron・開発サーバーを担当が起動すること(ヘッドレスのテスト実行は可)。
- 承認のない `package.json` の依存変更 / `pnpm-lock.yaml` / vendor ファイルの変更、ビルド途中の強制終了。
- **テスト期待値・性能上限の緩和**、`eslint-disable` / `@ts-ignore` / `@ts-expect-error` / `any` / 型の強制変換 `as`(`as const` を除く)による警告・型エラー封じ。
- 例外は 1 つだけ(共通規律 6): 指示書が明示した**仕様変更**を旧仕様で厳密に固定している既存テストは、新仕様の厳密な値へ置き換えてよい(検査を弱めるのではなく新仕様を厳密に検査する。report に列挙)。

- 包み `codex-run.sh <job名> <model> <sandbox> <指示書> [repo|self]`: `codex exec -m <model> -c model_reasoning_effort="<medium|high|xhigh>" -s workspace-write -C <リポジトリ> --add-dir <報告先> --add-dir <pnpm の store> --color never --json -o <報告先>/last.md - < <共通規律 + 指示書>` を実行し、`<報告先>/events.jsonl`(進行の記録)・`last.md`(最終メッセージ)・`status.txt`・`stderr.txt` を残す。推論の深さは model 別(terra=medium / sol=high / astra=xhigh。環境変数 `EFFORT` で上書き)。`self` は作業場所が報告先だけ(リポジトリは読むだけ。レビュー用)。
- 起動側 `codex-launch.sh <job名> <model> <指示書> [sandbox] [mode]`: 包みの**写し**を job のディレクトリに作ってから `nohup` で起動する(走行中に元を編集しても壊れない。10.21)。
- 状態 `codex-status.sh [job名…]`: 各 job の `走行中 / === DONE rc=N ===`、最終更新の分数、件数、最後の操作を 1 行ずつ。
- 担当が作った `.pnpm-store/` がリポジトリ直下にできることがある(`.gitignore` 済み)。push 前に消してよい。
- 1 job の消費の目安: terra の小 job で入力 60〜170 万(9 割超がキャッシュ)、sol の中 job で 400〜1,700 万、astra で 500〜1,100 万。出力は 1〜7 万。

### 7.2 指示書の置き場と報告先

- 指示書は作業用ディレクトリに `instr-<task>.md`。共通規律 `instr-common.md` を包みが先頭に付ける(`__OUT__` を報告先のパスに置換)。
- 報告先 `<作業用>/codex/<job名>/` に `progress.md` / `report.md` / `last.md`。**report.md を読んでから**着地の判断をする(統括の②)。差分は `git diff -- <所有ファイル>` で要点を確かめる。

### 7.3 コミットの待ち行列(統括の git 操作を機械化)

- 走り手 `commit-queue3.sh`(第 3 版): `queue/NNNN-*.job` を名前順に 1 件ずつ処理。job = `MSG=<メッセージファイル名>` と `FILES="<git add するパス…>"`(`[POST_ADD=<script>]` 任意)。手順: `git reset -q` → `git add $FILES` → **参照検査** `post-add-refcheck.py`(stage した TS の相対 import と help の目録 `.md` が HEAD ∪ stage に実在するか。10.20)→ `scripts/check.ps1 -Level Commit`(隔離 worktree で typecheck / lint / test / build。最大 3 回試行、60 秒待ち)→ `git commit -F`。失敗は `queue-failed/` へ。`queue/STOP` を置くと**その job の後に**止まる(job の前に置くと処理せずに止まる)。`queue/STOP` は走り手の起動時に消える。
- コミットメッセージの末尾に `Co-Authored-By: <あなたのモデル名> <noreply@…>` の行(利用者のリポジトリの慣習。Claude のときは `Claude Fable 5.1` と `Claude-Session:` の行)。
- **rules/06 10.11**: 走っている担当が編集中のファイルを待ち行列の job に入れない(job の `git add` は開始時の 1 回だけなので、開始後の編集は次の commit へ回るだけだが、開始前の編集が混ざると別の担当の書きかけを commit する)。担当が終わってから job を書く。所有が重なる担当を同時に走らせない。
- **同じファイルを触る担当は直列**(例: `kernelBridge.ts` は 11a-1 と 50 で直列にした)。
