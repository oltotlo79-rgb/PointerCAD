# 6. コミットとプッシュ

- git操作は統括(Claude)だけが行う。作業担当の成果を統括が検査した後、**タスクごとに都度**コミットする。リモートリポジトリを設定した後は `main` へプッシュする。
- コミットメッセージは日本語で、何を変え、何ができるようになったかが具体的に分かるように書く。利用者以外にも通じる言葉を使い、専門用語は極力避ける。
- `feat:`、`fix:` 等のプレフィックスは使わない。
- 本文末尾には実作者を示す `Co-Authored-By:` 行と、Claude Codeが指定するセッション行を付ける。
- 理由: タスク単位の追跡と復旧を容易にし、実作者を明示するため。作業担当には指示でgitへの書き込みを禁じているため、git操作は統括が行う。

# 7. コミット前の品質ゲート

- コミット前に統括が自分の環境で `scripts/check.ps1` を実行し、**全検査**を通す。作業担当の「合格しました」という報告を鵜呑みにせず、統括が再実行結果を確認する。
- 統括は `git diff --cached` の全文を読み、`--stat` の行数で代用せず、指示した各項目との対応、実装漏れ、対象外変更、勝手な仕様変更、禁止事項(依存の無断変更・警告封じ)がないことを照合する。
- **変えたパッケージのテストだけで合格としない。** モノレポ全体(`pnpm -r`)で検査する。パッケージ間の依存(`ui → model → kernel/expression`)があるため、上流の変更は下流を壊し得る。
- CI(`.github/workflows/ci.yml`)とgitフック(`scripts/hooks/pre-commit` / `pre-push`)でも同じスクリプト(`scripts/check.ps1`)を自動実行する(段階は §7.1 のとおり、pre-commit は E2E を除く4つ)。自動検査があることを、手元の確認を省く理由にしない。
- 理由: 自己申告だけでは検査環境の差や指示漏れを発見できず、不完全な変更が取り込まれるため。

# 7.1 検査の一覧(`scripts/check.ps1` が実行する)

検査は2段階に分ける。**コミットは速く、pushは厳しく。**

| # | 確認 | コマンド | `-Level Commit`(pre-commit) | `-Level Push`(pre-push / CI / 既定) |
|---|---|---|---|---|
| 0 | 作業ツリーの状態記録 | `-Level Commit` は写しの中で検査するため省略(下記参照)、`-Level Push` は `git status --porcelain --untracked-files=no`(検査前後で比較) | 省略 | 実行(全体) |
| 1 | 型検査 | `pnpm run typecheck` | 実行 | 実行 |
| 2 | 書き方の点検 | `pnpm run lint` | 実行 | 実行 |
| 3 | ユニットテスト | `pnpm run test` | 実行 | 実行 |
| 4 | 組み立て | `pnpm run build` | 実行 | 実行 |
| 5 | E2Eテスト | `pnpm run test:e2e`(このスクリプトが定義されている場合のみ) | 実行しない | 実行 |

- `scripts/check.ps1` の `-Level` の既定は `Push`(全部)。統括が手で実行するときも既定のまま全部を通す。`-Level Commit` を渡すのは `scripts/hooks/pre-commit` だけ。
- 段階を分ける理由: E2E は 50MB の WASM を含む Web 版のビルドとブラウザ起動を伴い、1回あたり十数秒かかる。「タスクごとに都度コミット」(§6)と両立させるため、コミット時は外す。**push と CI では必ず実行する**ので、検査から漏れることはない。
- E2E の直前に `pnpm exec playwright install chromium` を実行してブラウザの有無を確かめる。導入済みなら即座に終わる。CI 専用の導入ステップを `ci.yml` へ書かない(§7.2)。
- ルートの `package.json` に `typecheck` / `lint` / `test` / `build` のスクリプトが**1つでも無ければ検査は失敗**とする(fail-closed)。
- `package.json` がまだ存在しない間だけは「検査対象なし」として合格扱いとする。
- **テストが追跡対象のファイルを書き換えたら失敗とする**(#0の前後比較)。テストの実行だけで作業ツリーが汚れる状態は、実行順で結果が変わる不安定さの温床のため。
- **`-Level Commit` は「stage 済みの差分だけを写した別の作業ツリー」で検査する。** `git worktree add --detach HEAD` で写しを作り、`git diff --cached --binary` を `git apply` で写しへ載せ(新規・削除・改名を含む。適用できなければ理由を出して失敗する)、`node_modules`(根、`packages/*`、`apps/*`、`e2e` のうち実体があるもの)をコピーせずジャンクションで元へ向けてから、写しの中で型検査・書き方の点検・ユニットテスト・組み立てを行う。並列作業中の他担当の未 stage な書きかけは写しに一切現れないため、それらに影響されず統括がコミットできる(2026-09-05 実測: 対策前は待ち行列の先頭が90分・15回以上の再試行でも載らなかった。`rules/06-過去の失敗と対策.md` 10.7)。**根の `node_modules` だけは実体ディレクトリを作り直下の項目を個別にジャンクション/コピーする(丸ごとジャンクションにしない)**。pnpm(11系)の recursive 実行(`test`/`build`)は実行状態の記録先を根の `node_modules` 直下に置き、根自体がシンボリックリンク/ジャンクションだと `ERR_PNPM_UNSAFE_TASK_RUN_STATE_PATH` で実行そのものを拒否する実測があるため(`packages/*`・`apps/*` 配下にはこの制約が無く、従来どおり丸ごとジャンクションでよい)。検査の結果に関わらず、**ジャンクションを個別に外してから** `git worktree remove --force` で写しを片付ける(逆の順序にすると `git worktree remove --force` がジャンクションを辿って実体側の内容を削除する実測があるため、この順序を必ず守る)。実体(元の作業ツリー・index・node_modules)はどの経路でも一切変更しない。**pre-commit フックの子プロセスは `GIT_INDEX_FILE`(相対パス)等を継承するため、写しに対する git 呼び出し・写しの中で実行する pnpm はすべてこれらの環境変数を一時的に消してから行う**(`Clear-InheritedGitEnv` / `Restore-InheritedGitEnv`。消さないと `git worktree add` が写し側の相対パスへ迷い込み `fatal: Unable to create '.../.git/index.lock'` で失敗する実測がある。`rules/06-過去の失敗と対策.md` 10.8)。関数群は `scripts/lib/gitTreeGuard.ps1` が単一正本、自己試験は `scripts/check.selftest.ps1`。
- **#0 の前後比較は `-Level Push`(pre-push / CI)だけで行う。** 作業ツリー全体を `git status --porcelain --untracked-files=no` で比較する(従来どおり、並列編集が無い前提)。`-Level Commit`(pre-commit)は上記のとおり写しの中で検査し本物の作業ツリー・index には一切触れないため、比較そのものが構造的に不要(2026-09-05 に「stage 済みファイルだけを前後比較する」方式から「写しの中で検査するため比較を省く」方式へ変更した。`rules/06-過去の失敗と対策.md` 10.7)。比較関数は `scripts/lib/gitTreeGuard.ps1` が単一正本で、自己試験は `scripts/check.selftest.ps1`。
- **`-Level Commit` は tsc の増分ビルド(`tsconfig.tsbuildinfo`)キャッシュを持ち越さない。** 写しは毎回まっさらな `git worktree` のため、typecheck は基本的に毎回フルビルドになる。2026-09-05 実測でキャッシュ(`tsconfig.tsbuildinfo` と各パッケージの宣言出力)を写しへコピーしてみたが、値が食い違うことの多い並列開発中はコピーした内容がほぼ無効になり、tsc 側の整合性検証の手間だけが増えて**かえって遅くなった**(typecheck 単体: キャッシュコピー無し 18.0 秒 / コピーあり 27.5 秒)ため採用しなかった。実測ではコミット前検査全体(4段)の所要は写し方式でも数分台に収まり、機構自体の上乗せ(`git worktree add`+`diff`+`apply`+ジャンクション作成が約 2 秒、後片付けが約 0.3 秒)はごく小さい。
- **性能検査(NFR-PF-2 / NFR-PF-3)は #3 のユニットテストに含める。** 実体は `packages/kernel/src/worker/solidPerformance.test.ts` で、単一フィーチャー 500ms 以内・100 フィーチャーの全再計算 5 秒以内(未変更はキャッシュで短縮)を測り、超えたら `pnpm run test` が落ちる。上限は要件 `docs/requirements.md` §5.2 の数値そのままで**緩めない**(`rules/02-禁止事項.md`)。段を増やさないので `scripts/check.ps1` は変更しない。決定性検査は形状の再現性を測る手立てが要るためP6(入出力)で追加する。**新しい段を足すときは、この表と `scripts/check.ps1` を同じコミットで揃える(食い違わせない)。**
- **性能検査の上限判定は `-Level Commit`(pre-commit)では参考実測にとどめ、`-Level Push`(pre-push / CI)でだけ厳密に判定する。** 理由: 作業担当が並列にテストや E2E を走らせている間に統括がコミットすると、CPU 競合で境界値の検査が落ちるため(実測は `rules/06-過去の失敗と対策.md` 10.3)。環境変数 `POINTERCAD_PERF_STRICT` を `scripts/check.ps1` が `-Level` に応じて設定し、`solidPerformance.test.ts` の `expectWithinBudget` がそれを見て判定を切り替える。上限の数値は変えない。
- **ヘルプと取扱説明書の整合検査(NFR-MA-6)は push前検査(`-Level Push`)・CI には含めない。** リリース前検査(`scripts/check-release-ready.ps1`、05 §11.2)だけで行う(v1.9)。理由: 取扱説明書の生成とスクリーンショットの撮影はビルド成果物に対して行うものであり、コミット・pushの都度実行する検査には性質が合わないため。

# 7.2 CIとの関係

- CIは手元と同じ `scripts/check.ps1` を実行する(単一正本)。CI専用の検査コマンドを `ci.yml` に直接書かない。検査を増やすときは `check.ps1` へ追加すれば、手元・gitフック・CIの全てに同時に効く。
- CIはWindowsとLinuxの両方で実行する。デスクトップ版の対応OSがWindows/Linuxのため(要件§1.5)。
- 手元の検査合格を「CIに通った」と報告しない。push後にGitHub上の実際の結果を見るまで、CIに通ったとは書かない。手元とCIでは計算機・OS・CPUが異なり、浮動小数の丸めや性能が変わり得るため。
