# 指示書 R-7(第 3 回。取消検査の扱いを承認): 参照・投影の再計算を固定 2 巡から依存順の収束へ変える(レビュー 2026-09-07 R3-1、重大度 高、工数 L)

## 1. 目的と背景(コードで確認済み)

- `packages/model/src/part/recomputePart.ts:458-475`: 解決(`resolveWithOffsets`)→ solid 作成(`callSolids`)の後、面・辺・頂点の選び直し(`subShapes.refresh`)と投影の充填(`fillProjections`)を行い、どちらかが変わったら**もう一度だけ**解決 → solid 作成をする。二巡目の後に再度の選び直し・投影取得は無い。
- キャッシュが空の状態(保存を開き直した直後)で「solid A → A の面への投影スケッチ → solid B → B からの投影 → solid C」と連鎖すると、B は二巡目で初めて作られ、C 用の投影を取る巡回が無い。**保存を開き直したときだけ**形が未解決になる恐れがある(温かいキャッシュでは前回の結果で通る)。
- NFR-PF-3 のキャッシュは「結果を変えない最適化」であるべき。固定 2 巡は依存の深さを一般に覆えない。単純に 50 巡へ増やすのは無駄で、循環の隠蔽になる。

## 2. 変更の設計(レビューの具体策)

- 未解決の要求(参照の選び直し・投影)を**依存順に進めるスケジューラ**へ変える。暫定でよいのは「参照/投影の鍵集合が新たに解決された間だけ巡回し、上限は文書の依存段数(投影の元 → 先の連鎖の深さ)」、同じ未解決集合が続いたら停止して**対象フィーチャー ID つきの診断**を返す。
- 各巡回の前に **既存の `options.shouldCancel?.()`(`PartCancelToken`)** を確認し、真なら中止して取消の結果を返す。`options.generation` は開始時の値として結果に添えるだけでよい(最新世代を読む新しい API は**作らない**)。「UI 側で、実行中に新しい文書変更が queued された/世代が進んだときに `shouldCancel` を真にする配線」は**別タスク R-7b(ui の `attachKernel.ts`、後続)**とし、あなたの範囲外。あなたはモデル内で、**途中の巡回で真になる偽の `shouldCancel`** を使い「途中の結果を適用せず取消として返す」を検査する。
- 投影の無い文書では巡回が 1 回で終わり、いまと同じ回数の kernel 呼び出しになること(退行させない)。
- 循環(A の投影が B に、B の投影が A に依存)は上限で止まり、診断に両方の ID が出る。
